## ModDevGradle

- **Vanilla mode** (used by `common` until ADR-0002; `common` now compiles against NeoForge): `neoForge { neoFormVersion = "26.1.2-1" }` (or `enable { neoFormVersion = ...; disableRecompilation = ... }`) compiles against unmodified Minecraft with no NeoForge classes. Verified in the 2.0.147 sources (`NeoForgeExtension.setNeoFormVersion`, `ModdingVersionSettings`). A `net.neoforged.*` import in such a project is a compile error, except for `distmarker` (see below).
- `addModdingDependenciesTo(sourceSet)` makes that source set's `compileClasspath`/`runtimeClasspath` **extend** MDG's configurations (`ModDevArtifactsWorkflow.addToSourceSet`). It does not touch `api`/`implementation`, so Minecraft is **not** transitive through a project dependency.
- `disableRecompilation` defaults to `true` when the env var `CI=true` (since 2.0.136 according to the MDG README; the default itself is verified in the sources), otherwise false.
- `RunModel.gameDirectory` defaults to `<projectDir>/run`; our convention plugin overrides it to `runs/<project-path>/<run>` under the root.
- Run helpers on `RunModel`: `client()`, `clientData()`, `data()`, `server()`, `serverData()`; any other type via `type = "<name>"`.
- The settings plugin `net.neoforged.moddev.repositories` puts MDG's repositories in `dependencyResolutionManagement`, which makes `RepositoriesMode.FAIL_ON_PROJECT_REPOS` work.
- Vanilla-mode Minecraft jars land in `<project>/build/moddev/artifacts/vanilla-26.1.2-1{,-sources}.jar`; NeoForge ones in `minecraft-patched-26.1.2.109.jar` in the `neoforge` project. Read Minecraft sources from there.
- Vanilla mode only adds Minecraft to `main`. Other source sets (`api`, `test`) need `addModdingDependenciesTo`.
- Vanilla mode is not completely NeoForge-free: NeoForm brings `net.neoforged:mergetool`, so `net.neoforged.api.distmarker.{Dist,OnlyIn}` still compile.
- `mods {}` takes `SourceSet` objects, so pulling another project's source sets needs `evaluationDependsOn` (fine with the configuration cache, incompatible with Isolated Projects).
- A mod folder from another project in `mods {}` is not a compile dependency, so an IntelliJ run config (which builds only its own module before launch) runs that mod's stale classes; a Suite Client launch crashed with `NoSuchMethodError` this way. `RunModel.taskBefore(...)` fixes it: the Gradle `run*` task `dependsOn` those tasks, and the generated IntelliJ config gets a Gradle "before launch" step running them (`ModDevRunWorkflow`, `IntelliJIntegration`). Our `loadMod` adds the other mods' `classes`/`apiClasses` tasks (and the mod's own `common` ones, see "IDE runs, common resources" below) to every run this way, and `suiteClient` adds its extra mods' tasks only to the suite run. Run configs pick it up on the next Gradle sync. This only helps while IntelliJ delegates builds to Gradle (the default): with `delegatedBuild=false` in `.idea/gradle.xml`, MDG points the mod folders at IntelliJ's own `out/` directories, which the Gradle step never refreshes.
- Gradle identifies projects by `group:name`. All our `common`/`neoforge` projects share names, so the convention plugin sets a per-mod group; a shared group makes a `project(":<mod>:common")` lookup resolve to the wrong project.

- In plain Kotlin files under `build-logic/src/main/kotlin` (not `.gradle.kts` scripts) the `prop = value` assignment for Gradle `Property`s is unavailable; use `.set(...)`. Inside `runs.configureEach { }`, a bare `project` resolves to MDG's deprecated `RunModel.getProject()`; qualify it (`this@Extension.project`).

- There is no `localRuntime` configuration in MDG 2.0.147, and for 26.1 (`VersionCapabilities.legacyClasspath()` false) adding anything to `additionalRuntimeClasspath` is forbidden (`ModDevRunWorkflow.forbidAdditionalRuntimeDependencies`). A run's classpath is its source set's runtime classpath, so a `runtimeOnly` mod (JEI) joins **every** run of that project, server and GameTest runs included. Addon projects do not see `lib:neoforge`'s runtime dependencies (Lib is only a mod folder there), so each project that wants JEI in its dev client declares it itself. Only `common` projects are published, so `runtimeOnly` in a `neoforge` project reaches no POM.

## neoforge.mods.toml

- `loaderVersion` is the **javafml** version, `[1,)` (Documentation `gettingstarted/modfiles.md`), not the FML version (11.x).
- URLs (FML 11.0.15 and NeoForge 26.1.2.109 sources): `issueTrackerURL` is a top-level key (`ModFileInfo.getIssueURL`,
  shown in crash reports); `displayURL` sits in a `[[mods]]` block and only the mod list screen reads it
  (`ModListScreen`). `ModInfo` also reads `modUrl` and `updateJSONURL` per mod.
- **Do not** add `services = [...]`: in dev (and without a `module-info`) the mod is an automatic module and FML fails with "Automatic modules can not declare service dependences". The docs list the field, but it only works for explicit modules. Automatic modules may use any service and publish `META-INF/services` providers, so `ServiceLoader.load(Platform.class, Platform.class.getClassLoader())` works without it (verified with `runServer`).

## Error Prone (verified with `./gradlew build`)

- `ReferenceEquality` flags `==` between objects of interface types (e.g. two `EnergyHandler`s), and warnings fail the build. Where identity is the point (capability instances), suppress it on the method with a one-line justification.
- `ArrayRecordComponent` fires for a record with an array component, and fails the build like any warning; use a fastutil list or a small final class.
- `ComplexBooleanConstant` rejects expressions such as `true || x`, so a quick hack to disable a check (e.g. to see a test fail) needs a non-constant form.
- Error Prone 2.50's `StringConcatToTextBlock` threw an internal exception ("An unhandled exception was thrown by the Error Prone static analysis plugin", `matchLiteral`) on a single string literal longer than the 120-column line inside a `LOGGER.info(...)` call in a GameTest; splitting the literal into a `"..." + "..."` concatenation compiled.
- `StringSplitter` rejects `String.split(String)`; use Guava's `Splitter.on('_').omitEmptyStrings().split(s)` (Guava ships with Minecraft).
- `checkCommonImports` also scans `common`'s test sources, so a NeoForge import in a JUnit test needs the `// PLATFORM-LEAK:` marker too.
- The marker must be on the reference's line or on the comment line **directly** above it: a two-line comment that starts with `// PLATFORM-LEAK:` and wraps onto a second line is reported. Put the reason first and end with `// PLATFORM-LEAK: see above.`
- `ReferenceEquality` also fires for `==` between two `Fluid`s; use `equals`.
- `ReferenceEquality` fires for `==` between two `Item`s too (seen in `ProcessingGameTests`); use `equals`.
- `IdentityHashMapUsage` fails the build for `Map<K, V> m = new IdentityHashMap<>()`; declare the variable as `IdentityHashMap`, or use a `HashMap` when the key keeps `Object`'s identity `equals` anyway.
- `UnnecessaryLambda` rejects a lambda stored in a constant (`static final Predicate<T> ANY = r -> true`); write a private static method and pass a method reference, which is non-capturing and so allocates nothing per use. `UnusedVariable` fails the build for a field that is written but never read.
- `ObjectToString` fails the build when a final class without its own `toString()` is concatenated into a string, e.g. in a test's failure message; print an id or position instead.
- `EnumOrdinal` fails the build on any `Enum.ordinal()` call; where an ordinal only travels to a client of the same build (menu data slots, payloads), suppress it with a one-line reason. `OperatorPrecedence` wants parentheses around `a && b` inside `x || a && b`.
- `ImmutableEnumChecker` fails the build for an enum with a `TagKey` field: `TagKey` is a record of immutable parts but lacks `@Immutable`. Suppress it on the field with a one-line reason.
- `UnnamedVariable` fails the build for an unused lambda parameter with a name (`computeIfAbsent(k, unused -> ...)`); Java 25 wants `_`. `ReferenceEquality` also fires for `==` between two `Item`s; use `equals` or `Optional.filter(item::equals)`.
- Spotless's Eclipse formatter packs enum constants with constructor arguments onto as few lines as fit, mid-argument; a Javadoc comment on each constant keeps one constant per line.
- `EnumOrdinal` also rejects stepping through an enum by index (`values()[ordinal() - 1]` for "the previous constant"); an exhaustive `switch` over the constants compiles and stays checked when a constant is added (`CableSize.half`).
- To compare a recipe output's `Holder<Item>` with an `Item` without tripping `ReferenceEquality`, use `holder.is(item.builtInRegistryHolder())`: 26.1.2's `Holder.Reference.is(Holder)` compares the two keys (patched `Holder.java`; used in `MetallurgyIvGameTests`).

- `FloatCast` wants parentheses around a cast inside arithmetic (`((int) a) * n`); `RefactorSwitch` rejects a
  statement switch whose every case only returns (write `return switch (...) { ... };`); `NotJavadoc` fails the build
  when an edit leaves two `/** */` comments above one member. `ReferenceEquality` also fires for `!=` against a record
  constant used as a sentinel; keep a boolean instead.
- javac doclint on JDK 25 (verified on the api compile tasks): the `missing` group also reports every method without
  `@param`/`@return`, not only missing comments, so it is off (`-Xdoclint:all/protected` plus a separate
  `-Xdoclint:-missing` argument; the single form `all,-missing/protected` still reported missing tags). The rest of
  doclint works under Error Prone and `-Werror` fails on a broken `{@link}`. `checkApiJavadoc` (build-logic) checks that
  comments exist; it parses with `JavacTask.parse()`, whose trees keep doc comments for `DocTrees.getDocCommentTree`.
- NullAway in Lib's api source set (verified compiling `lib.api.energy`, 2026-10-15): `array[i] = null` fails ("Writing
  @Nullable expression into array with @NonNull contents"), and declaring the array `@Nullable T[]` there makes every
  element read nullable, unlike the main source set (`NetworkManager.graphs`). Clearing slots with
  `Arrays.fill(array, from, to, null)` compiles in both.

## FML

- The dev client cannot start from Claude Code's sandboxed shell: early display fails with "Failed to find a primary monitor" (GLFW). Use `runServer` / `runGameTestServer` for headless checks and leave `runClient` to the owner. It fails the same way with the sandbox disabled from an agent session (tried for the JEI plugin, M2 task 10), so no agent can check a client log.
- A dedicated `runServer` needs `eula=true` in `runs/<project>/server/eula.txt` (gitignored).
- Production server (verified with `scripts/smoke-server.sh`, 26.1.2.109, Windows): `java -jar neoforge-<v>-installer.jar --installServer <dir>` (installer from `maven.neoforged.net/releases/net/neoforged/neoforge/<v>/`) installs in about 6 s; start it from `<dir>` with `java @user_jvm_args.txt @libraries/net/neoforged/neoforge/<v>/{win,unix}_args.txt nogui` (relative paths, classpath separator per OS; `user_jvm_args.txt` is comments only). `server-port=0` binds a free port; "stop" on stdin stops it, saving again after "Stopping server". FML lists each loaded mod file as ` - <modid> (jar(mods/<file>))`, a jar-in-jar one as ` - guideme (jar(mods/maxtech_storage-<v>.jar > guideme-<v>.jar))`. A client class referenced from a mod constructor fails with `NoClassDefFoundError: net/minecraft/client/Minecraft` and a crash report. Harmless noise: log4j's `DebugFile` appender reports `NoClassDefFoundError` for netty's `kqueue`/`epoll` `Native` (the other OS's transport) when it renders netty's startup probe.
- Dev game processes run `net.neoforged.devlaunch.Main`, with the mods in `-Dfml.modFolders=<modid>%%<dir>...` **before** the main class; the run directory is not on the command line. **Never `pkill -f devlaunch.Main`**: the CI runner is the same machine, and that killed a CI GameTest run (exit 143). The mod folders contain the checkout path, so stop only your own checkout's games with `scripts/stop-dev-games.sh` (on macOS and Linux it runs `pkill -f "%%$(pwd)/[a-z]+/neoforge/build/"`, on Windows an equivalent PowerShell command-line match; `DRY_RUN=1` lists the matches first). It matches neither worktree agents' games (their paths continue with `.claude/worktrees/`) nor CI's (`~/actions-runner-maxtech/_work` and, since 2026-09-30, the second runner's `~/actions-runner-maxtech-2/_work`). Never run `./gradlew --stop` either: it stops every Gradle daemon on the machine, including CI jobs and other worktrees' builds (it killed PR #32's CI GameTests). `pkill -f fml.startup.Server` matches nothing and leaves the server holding port 25565, so the next `runServer` fails with "FAILED TO BIND TO PORT".
- Dev mod folders: `InDevFolderLocator` reads `MOD_CLASSES` or the `fml.modFolders` system property (`modid%%path` entries, path-separator delimited), groups the folders per mod ID into one virtual jar, and loads it **whether or not those folders are on the JVM classpath**. That is why `neoforge` projects take `common` as `compileOnly` and still load it at dev runtime via `mods {}`.
- Each mod's jar is its own module, so a mod's resources are read through a class from that mod: `anchor.getResourceAsStream("/<modid>/presets/standalone.json")` with a class of that mod finds the mod's resource. Whether a class of another mod could see it was not tested; `PresetConfig` avoids relying on it.

## Reading other mods' files at construction (verified in the FML 11.0.15 loader sources)

- **The mod list is complete before any mod constructs.** `ModLoader.gatherAndInitializeMods` builds `ModList.of(modFiles, sortedMods)` and calls `setLoadedMods(containers)` for every mod, then `constructMods`.
- **Reading a file from another mod's jar without its classes:** `ModList.get().getModFileById(modId).getFile().getContents()` is a `JarContents` (`net.neoforged.fml.jarcontents`); `readFile(relativePath)` returns the bytes or `null` when absent (`openFile`, `containsFile` likewise). This avoids `Class.getResourceAsStream`, which in a named module only sees that module's own resources. `getModFileById` returns `null` for an unknown id (a plain map lookup, unannotated).

## IDE runs, common resources and the suite GameTest run (verified in the MDG 2.0.147 sources, with an init script printing each run's `tasksBefore`/`loadedMods`, and by `runSuiteGameTestServer`)

- An IntelliJ run builds its own `neoforge` module only. `common` is a `compileOnly` project dependency there, so that build compiles `common`'s classes but never runs its `processResources`; `common/build/resources/main` stays missing or stale, and FML simply leaves a missing folder out of the mod. `loadMod` therefore lists the mod's own `common` `classes`/`apiClasses` in every run's `taskBefore` too. The generated IntelliJ config runs `run.getTasksBefore()` as one Gradle "Prepare" step before launch (`IntelliJIntegration.addIntelliJRunConfiguration`).
- A client mod-construction crash report shows only `ExceptionInInitializerError: null` with no cause frames, and the cause is not in `debug.log` either. A `gameTestServer` or `server` run prints the full `Caused by:` chain to the console, as does a temporary try/catch in the mod constructor.
- `neoForge.runs.named(name) { ... }` added after another plugin's `runs.configureEach { ... }` runs after it, so it can override what the `configureEach` set (here `loadedMods`, which `suiteClient` narrows for every run not named `suiteClient`).

## Lib and its addons as separate mods (ADR-0014 step 2; verified by `runGameTestServer` of every mod, `runData` and `build`)

- A mod's config fires `ModConfigEvent.Reloading` on the mod bus of the container it was registered on, never on
  another mod's. Lib's `ServerConfig` registers under `maxtech_lib`, so a GameTest environment in an addon that switches
  a Lib value must join Lib's bus too:
  `ModList.get().getModContainerById(MaxtechLib.MOD_ID).map(ModContainer::getEventBus).ifPresent(bus ->
  bus.addListener(ModConfigEvent.Reloading.class, ...))`.
- `ServiceLoader.load(Platform.class)` finds the implementation through `META-INF/services/<interface FQN>` in Lib's
  neoforge resources while the interface lives in Lib's common source set: in dev both are one mod (one module), and in
  a jar one file.
- A `common` project's `api` source set does not see the `api(...)` dependencies of `main`. An addon whose api names
  Lib's api types adds `"apiCompileOnly"(project(":lib:common", "modApi"))`.
- A block entity type shared by blocks other mods register can collect them by class when its supplier runs: block
  entity types register after every mod's blocks, so `BuiltInRegistries.BLOCK` is complete there (Lib's `CONDUIT` type
  over every `ConduitBlock`).
- A tag file that includes a tag no loaded pack defines fails to load ("missing following references") and the tag is
  empty. Declare a tag no mod may fill as an empty tag in your own data. Lib's `maxtech_lib:acts_as/wrench` only
  includes `c:tools/wrench`, which NeoForge itself defines.

## Plain JUnit and the vanilla bootstrap (M6c2 area G; verified by a throwaway JUnit test in `:storage:common:test`)
- `SharedConstants.tryDetectVersion(); Bootstrap.bootStrap();` in a plain JUnit test (no MDG `junit` run) fails with `ExceptionInInitializerError` caused by `IllegalStateException: There is no current FML Loader`: NeoForge's patched registries need FML. So `ItemKey.of(Items.X)` and other registry-backed keys cannot be built in `common`'s JUnit tests; keep the logic under test generic over its key type (Storage's `HistoryRings<K>`, tested with strings) or test it in a GameTest.

# NeoForge APIs

## NeoForge APIs (verified against `~/mc-reference/NeoForge` on `26.1.x`, commit c0bf100)

- Identifiers are `net.minecraft.resources.Identifier` (`fromNamespaceAndPath`, `parse`, `withDefaultNamespace`). There is no `ResourceLocation`.
- `DeferredRegister.create(ResourceKey<? extends Registry<T>>, String)`; `register(String, Supplier<? extends I>)` and `register(String, Function<Identifier, ? extends I>)` return a `DeferredHolder<R, I>` (implements `Holder<R>` and `Supplier<I>`; `getId()`, `getKey()`); `register(IEventBus)`. Blocks and items need the id before construction (`Properties.setId`), hence the `Function` overload.
- `ModList.get().getModContainerById(id)` returns an `Optional`; `ModContainer.getEventBus()` is `@Nullable`; `ModContainer.registerConfig(ModConfig.Type, IConfigSpec)`.
- `IEventBus.addListener(Class<T>, Consumer<T>)` exists (bus 8.0.5).
- `BlockCapability.createSided(Identifier, Class<T>)` creates the capability or returns the existing one. Lookup: `level.getCapability(cap, pos, side)` (`ILevelExtension`).
- Model data: a block entity hands render data to its baked model only by overriding `IBlockEntityExtension.getModelData()` (returns `ModelData.EMPTY` by default) and calling `requestModelDataUpdate()` when it changes; `ModelDataManager.refreshAt` reads it on the main thread. Models read it in `collectParts` via `level.getModelData(pos)` and must not touch block entities there (meshing threads). No event supplies model data from outside the block entity (checked in `~/mc-reference/NeoForge`, PR #10 review).
- Item capabilities: `ItemCapability.createVoid(Identifier, Class<T>)` (create-or-get, like blocks); query with `stack.getCapability(cap)` (`IItemStackExtension`).
- `BlockCapabilityCache.create(cap, ServerLevel, pos, context)` and the overload with `(BooleanSupplier isValid, Runnable invalidationListener)`; read with `getCapability()`. The listener must not call `getCapability()` or touch the level, and only fires after `getCapability()` was called since the last invalidation (Javadoc in `BlockCapabilityCache`).
- Networking: `RegisterPayloadHandlersEvent.registrar(version)` gives a `PayloadRegistrar` with `playToClient` / `playToServer` / `playBidirectional(type, StreamCodec<? super RegistryFriendlyByteBuf, T>, IPayloadHandler<T>)`. Handlers run on the **main thread** by default (`HandlerThread.MAIN`). `IPayloadHandler.handle(T, IPayloadContext)`; `IPayloadContext.player()`.
- Sending: `PacketDistributor.sendToPlayer(ServerPlayer, payload, ...)` and friends are in `net.neoforged.neoforge.network`. `sendToServer` moved to `net.neoforged.neoforge.client.network.ClientPacketDistributor`, which is in the **client** source set.
- **Server config files live in the game's `config/` directory** (e.g. `runs/<project>/server/config/<modid>-server.toml`), not in `<world>/serverconfig/` as in older versions (verified with `runServer`).
- `ModConfigSpec.ConfigValue.set(v)` changes the value without writing; `ModConfigSpec.save()` writes the file and fires `ModConfigEvent.Reloading` (mod bus), so a load listener that saves must guard against re-entry. `ModConfig.getFullPath()` is `null` when values were not loaded from a file (a client's synced server config).
- `ModContainer.registerConfig(...)` returns `void`; match `ModConfigEvent.Loading/Reloading` to your config by `event.getConfig().getSpec()` (identity; `ModConfigSpec` has no `equals`). Enum values are written upper case (`"TRUNCATE"`) and read case-insensitively.
- Config values **throw** `IllegalStateException("Cannot get config value before config is loaded.")` when read before their file loads (`ConfigValue.get` -> `getRaw`); they do not fall back to defaults. Server config loads with the world. `get()` caches: a value read while loaded keeps answering after the file unloads; one never read throws. GuideME scenes (and its web export) load block entities on a client with no server config, so Storage's server values go through `LoadedOrDefault` (default while unloaded, issue #333).
- Config: `ModConfigSpec.Builder` has `comment`, `push`, `pop`, `define(path, boolean)`, `defineInRange` (int/long/double), `defineEnum(path, E)`, `build()`. `BooleanValue`/`IntValue`/`LongValue`/`DoubleValue` implement `BooleanSupplier`/`IntSupplier`/`LongSupplier`/`DoubleSupplier`; `EnumValue` is a `Supplier<E>`.
- Events: `FMLCommonSetupEvent` (mod bus); `ServerStartingEvent`, `ServerStoppedEvent` (`getServer()`), `LevelTickEvent.Post` (`getLevel()`) on `NeoForge.EVENT_BUS`.
- Custom registries: `NewRegistryEvent` (mod bus) `event.create(new RegistryBuilder<>(key).sync(true))` creates and registers one; it then sits in `BuiltInRegistries.REGISTRY` under `key.identifier()`, so common code can read it back without a NeoForge import. `DeferredRegister.create(key, modid)` (our `Platform.registry().registrar`) works for such a key unchanged (verified with the conduit type registry and GameTests).
- `IBlockExtension.onDestroyedByPlayer(state, level, pos, player, toolStack, willHarvest, FluidState)` runs on **both** sides and must remove the block itself; returning `false` keeps the block and skips `playerDestroy`, so no loot drops (verified by GameTest). `willHarvest` is false in creative. A `Block` subclass can call `super.onDestroyedByPlayer(...)` without importing `IBlockExtension`.
- Capabilities are invalidated automatically on chunk load/unload, block entity load/unload and block entity placement/removal (`IBlockCapabilityProvider` Javadoc; the patched `BlockEntity.setRemoved`/`clearRemoved` call `invalidateCapabilities()`). Anything else that changes what a provider returns must call `level.invalidateCapabilities(pos)` itself. Verified by `EnergyGameTests` (a replaced sink is found again through a `BlockCapabilityCache`) and Lib's `energy_edge_neighbour_change` (the cache listener fires when a block entity is placed at an empty spot and when `setBlock(pos, AIR)` removes it).
- `RegisterCapabilitiesEvent` (mod bus): `registerBlockEntity(BlockCapability, BlockEntityType, (blockEntity, context) -> T)` and `registerBlock(capability, (level, pos, state, blockEntity, context) -> T, Block...)`. From our `BlockLookup`, get the capability with `NeoForgeBlockLookup.of(lookup).capability()`.

### Transfer API (`net.neoforged.neoforge.transfer`, verified in the sources and by GameTests)

- `Capabilities.Item.BLOCK` and `Capabilities.Fluid.BLOCK` are `BlockCapability<ResourceHandler<ItemResource | FluidResource>, @Nullable Direction>` (both proxyable). There is no `IItemHandler`/`IFluidHandler`.
- `ResourceHandler<T extends Resource>` (`transfer.resource.Resource`): `size()`, `getResource(i)`, `getAmountAsLong(i)`, `getCapacityAsLong(i, resource)` (a hint; empty resource = general capacity), `isValid(i, resource)`, `insert(i, resource, amount, TransactionContext)` and `extract(i, ...)` returning the amount moved. The index-free `insert(resource, amount, tx)`/`extract(...)` are defaults that loop over the indices; override both overloads when the handler decides placement itself. Implementations must start with `TransferPreconditions.checkNonEmptyNonNegative(resource, amount)` and must honour transactions.
- `ItemResource`: `EMPTY`, `of(ItemStack)` (the count is dropped), `of(ItemLike)`, `toStack(count)`, `getMaxStackSize()`, `isEmpty()`. `ItemResource.CODEC` rejects empty resources (`OPTIONAL_CODEC` accepts them) and needs registry context (a block entity's `ValueOutput` has it). `FluidResource`: `EMPTY`, `of(Fluid)`, `CODEC`. Amounts are `int`, mB for fluids.
- `transaction.Transaction`: `openRoot()` throws if a transaction is already open (or closing) on the thread; `open(parent)` nests. `commit()` keeps the changes; closing without committing (try-with-resources) rolls them back, which is how you simulate. `TransactionContext` is what handlers receive; only `depth()`. Works in plain JUnit without `Bootstrap` (`FluidBudgetTest`).
- `transaction.SnapshotJournal<T>` is the base for transaction-aware state: call `updateSnapshots(tx)` right before changing state, implement `createSnapshot()`/`revertToSnapshot(T)`, optionally `releaseSnapshot(T)` (pooling) and `onRootCommit(T originalState)`, which runs right after the root transaction closes successfully (irreversible side effects such as `setChanged()` go there). A nested commit moves the snapshot up one level; an inner abort reverts only its part. `RootCommitJournal(Runnable)` is a stateless journal that only fires the callback.
- Hoppers push through `VanillaInventoryCodeHooks.insertHook`: it skips the target when `ResourceHandlerUtil.isFull(handler)` (every index `amount >= capacity`), else opens a root transaction, inserts one item and commits. The target is looked up with side `facing.getOpposite()`, the face of the target that touches the hopper. A handler that reports capacity 0 therefore stops a hopper without an insert call. If the block exposes no item capability at all, `HopperBlockEntity.getContainerOrHandlerAt` falls through to `VanillaInventoryCodeHooks.getEntityContainerOrHandler`, an entity search over the target block's AABB on every push attempt, so refusing a side with a present, zero-capacity handler is cheaper for hoppers than returning `null`.
- `fluid.FluidStacksResourceHandler(size, capacity)` is a ready-made tank (`capacity` is a protected field); `StacksResourceHandler` implements `ValueIOSerializable`.
- `item.ItemStacksResourceHandler(size)` is the slot equivalent. Subclasses see the live list as the protected `stacks`, so reading a slot allocates nothing. `set(index, resource, amount)` fires `onContentsChanged` at once; `insert`/`extract` fire it once per changed index when the root transaction commits, never on a rollback. `deserialize(ValueInput)` replaces the list with the saved one **including its size**, so a handler whose slot count changed must resize after loading. `getResourceFrom(ItemStack.EMPTY)` gives the empty resource without importing `ItemResource`.
- `StacksResourceHandler#isValid(index, resource)` is the filter hook: an override refuses insertion and reports capacity 0 for refused resources; `set(...)` and `deserialize` do not check it (verified by `combustion_generator_solid_fuel_into_cable`, which fails with a filter that accepts everything).
- Buckets on a block: `transfer.fluid.FluidUtil.interactWithFluidHandler(Player, InteractionHand, @Nullable BlockPos, ResourceHandler<FluidResource>, @Nullable TransactionContext)` first tries to fill the held item from the handler, then to empty it into the handler, swaps the item in hand (lava bucket -> bucket in survival) and plays the sound; `null` opens its own root transaction. The overloads without a transaction argument are deprecated for removal. It works on a GameTest mock survival player (verified by `combustion_generator_bucket_fills_tank`).
- `ResourceHandlerUtil.insertStacking(handler, resource, amount, @Nullable TransactionContext)` fills matching indices before empty ones; with `null` it opens and commits its own root transaction. `Transaction.openRoot()` works from the level tick event (no transaction is open there); closing it uncommitted is a free simulation (`RecipeLogic.outputsFit`). `ItemResource.of(ItemStackTemplate)` and `FluidResource.of(Holder<Fluid>)` exist; both return the shared default resource when there are no components.
- `TransactionManager` keeps one `Transaction` per nesting depth per thread and reuses it, so `Transaction.openRoot()` allocates only the first time a depth is reached; what a transaction costs each time is its journals' snapshots: `StacksResourceHandler` snapshots a changed index with `copyOf(stack)`. A per-tick writer to a tank it owns can skip both with `set(index, resource, amount)` on the handler, as the boilers do (verified in the NeoForge sources).
- Every `Transaction.open(parent)` and `openRoot()` calls `StackWalker.getCallerClass()` (NeoForge 26.1.2.109 sources), and `ResourceHandlerUtil.insertStacking(handler, resource, amount, tx)` always opens its own nested transaction inside `tx`. In a profile of busy ports the stack walks were about a sixth of an operation's time, so a hot path should not open transactions it does not need (`PortTransfers.insertStacking` is the loop without one).
- **FE (Forge Energy) in 26.1 is part of the transfer API**: `transfer.energy.EnergyHandler` (no `IEnergyStorage`), with `getAmountAsLong()`, `getCapacityAsLong()` (a hint) and `insert(int, TransactionContext)` / `extract(int, TransactionContext)` returning the amount moved; implementations must honour transactions (`SnapshotJournal`) and reject negative amounts (`TransferPreconditions.checkNonNegative`). The block capability is `Capabilities.Energy.BLOCK`, a `BlockCapability<EnergyHandler, @Nullable Direction>` named `neoforge:energy_handler` (proxyable); `Capabilities.Energy.ITEM` is `ItemCapability<EnergyHandler, ItemAccess>` and there is an `ENTITY` one. Ready-made: `SimpleEnergyHandler(capacity[, maxInsert, maxExtract])` (int amounts, `ValueIOSerializable`, `onEnergyChanged` after the root commit), `EnergyHandlerUtil.move(from, to, amount, @Nullable TransactionContext)` (simulates the extract, inserts, then extracts what was inserted; `null` opens its own transaction) and `isFull`. Since `BlockCapability.createSided` is create-or-get and checks the type class, `Platform.capabilities().sided(Identifier.fromNamespaceAndPath("neoforge", "energy_handler"), EnergyHandler.class)` returns NeoForge's own capability, so `common` reaches FE without importing `Capabilities`. `SnapshotJournal.releaseSnapshot(T)` is called for every snapshot, after `onRootCommit` for the root one, so snapshots can be pooled (verified in the NeoForge sources and by `fe_converter_*` GameTests and `FeConverterEnergyTest`, which runs transactions in plain JUnit).
- **Pulling FE is the same `EnergyHandlerUtil.move(source, ours, amount, null)` with the neighbour as `from`**: it simulates the neighbour's extract, inserts into ours and extracts what we took, all in one root transaction, so a pull never takes more than our room. `SimpleEnergyHandler.set(int)` overwrites the amount and calls `onEnergyChanged` at once, but it is a plain field write with no block update, so a neighbour that caches the handler gets no event; `SimpleEnergyHandler(capacity)` has per-operation limits equal to the capacity (NeoForge sources; `fe_converter_pulls_fe`).

- **Capability caches** (`~/mc-reference/NeoForge` 26.1.x, `BlockCapabilityCache`, `CapabilityListenerHolder`):
  `getCapability()` throws IllegalStateException once the cache's `isValid` check returned false, and when called
  from its own invalidation listener, so a replaced owner needs a new cache, and the listener should only flag work
  for the owner's next tick. The level holds listeners as `WeakReference`s: a cache or listener the owner doesn't keep
  in a field stops firing after a GC.
- **Moves between handlers** (`ResourceHandlerUtil.moveInternal`, same sources): a handler may accept or yield only
  the exact amount it simulated, even when it behaves, so `extract(inserted)` can return less than `inserted`. Do the
  insert and the extract in one transaction and commit only when the two amounts match; amounts are ints, so cast a
  long network amount with saturation and loop.
- **Menu slots over handlers** (NeoForge 26.1.2.109 sources, `menu_slots_*` GameTests): `transfer.item.ResourceHandlerSlot(handler, IndexModifier, index, x, y)` extends `world.inventory.StackCopySlot` (outside common's allowlist, but a subclass never names it): `getItem()` returns a fresh copy each call, `set` writes through the `IndexModifier` (`StacksResourceHandler::set` fits), so vanilla's click paths and slot sync work on copies and write back whole. `mayPlace`/`mayPickup` are overridable. `PlayerInventoryWrapper.of(player).getSlot(i)` uses `Inventory` indices (0-8 hotbar, 9-35 main) and its root commit calls `player.containerMenu.broadcastChanges()` on the server; `RangedResourceHandler.of(handler, start, end)` and `new CombinedResourceHandler<>(a, b)` give ordered targets for `insertStacking`.
- **Fluid containers on the cursor**: `ItemAccess.forPlayerCursor(player, menu).oneByOne().getCapability(Capabilities.Fluid.ITEM)` is the carried item's fluid handler; with a stack of buckets one is used and the changed one goes into the inventory. `ResourceHandlerUtil.moveFirst(from, to, filter, amount, tx)` moves only what both sides accept (a bucket takes or gives exactly 1000 mB, so a 500 mB tank fills nothing), `null` when nothing moved. `ItemAccessFluidHandler(access, DataComponentType<SimpleFluidContent>, capacity)` is a container that fills and empties in any amount (a test flask). `FluidUtil.triggerSoundAndGameEvent(resource, level, pos, player, pickup)` plays the bucket sound.
- **Menu open data** (`IPlayerExtension.openMenu` Javadoc): the extra data writer is limited to 32600 bytes. Send
  large contents (a terminal's list) as payloads after the menu is open.

## Fluids (verified in the NeoForge and patched sources and by GameTests unless marked)

- A mod fluid is a `Fluid` plus a NeoForge `FluidType` (`net.neoforged.neoforge.fluids`, `new FluidType(FluidType.Properties.create().density(...)...)`). The type registry is `neoforge:fluid_type` (`NeoForgeRegistries.Keys.FLUID_TYPES`); `common` builds the key with `ResourceKey.createRegistryKey(Identifier.fromNamespaceAndPath("neoforge", "fluid_type"))` rather than importing NeoForge's registries package, and a `Platform.registry()` registrar works for it. `Fluid#getFluidType()` is a patched method a subclass overrides without importing `IFluidExtension`.
- Registration order (`GameData.getRegistrationOrder`): attribute, data components and particle types, then vanilla's order (fluids before blocks and items), then every other registry sorted by id, so **fluid types register after fluids and items**. A fluid and its bucket must read their `FluidType` lazily (a supplier), never in a constructor.
- A fluid that only lives in containers can extend `Fluid` directly like vanilla's `EmptyFluid`, with no source/flowing pair and `createLegacyBlock` returning air. Vanilla's `BucketItem.emptyContents` places only a `FlowingFluid` and returns false otherwise, so its bucket cannot be emptied into the world.
- NeoForge registers `Capabilities.Fluid.ITEM` (a `BucketResourceHandler`) for every item whose class is **exactly** `BucketItem` (`CapabilityHooks`, `item.getClass() == BucketItem.class`), so a mod's plain `BucketItem` fills and empties machine tanks through `FluidUtil.interactWithFluidHandler` with no registration of its own. Filling an empty bucket asks `FluidType.getBucket(stack)`, i.e. the fluid's `getBucket()`.
- A fluid type's name key defaults to `fluid_type.<namespace>.<path>` of its registry id (`FluidType.getDescriptionId`); `FluidStack`/`FluidResource.getHoverName()` use it.
- Fluid tags in datagen: vanilla `net.minecraft.data.tags.FluidTagsProvider(PackOutput, CompletableFuture<HolderLookup.Provider>, String modId)` (the mod id overload is a NeoForge patch), `tag(TagKey<Fluid>).add(fluid)`; output lands in `data/<ns>/tags/fluid/`. A tank filter can test `resource.typeHolder().is(tag)`.
- Client (sources only, not seen in a client): still and flowing sprites are no longer on `IClientFluidTypeExtensions`; register `new FluidModel.Unbaked(Material still, Material flowing, @Nullable Material overlay, @Nullable FluidTintSource)` for the fluid with `RegisterFluidModelsEvent` (mod bus, client, fired on a worker thread during model loading). A null tint is ambiguous with a deprecated `BlockTintSource` constructor; cast it. A fluid without a model gets `FluidStateModelSet`'s missing model instead of failing.
- A fluid's baked sprites and tint at runtime (client): `Minecraft.getInstance().getModelManager().getFluidStateModelSet().get(fluid.defaultFluidState())` is the vanilla `FluidModel` record (`stillMaterial()`, `flowingMaterial()` as `Material.Baked`, nullable `overlayMaterial()`, NeoForge's nullable `fluidTintSource()` whose `color(FluidState)` is the tint); it is replaced on each resource reload. `IClientFluidTypeExtensions` only keeps the camera overlay and fog. Light: `FluidType.getLightLevel()` (lava 15; the positional overload defaults to it), and `fluidState.createLegacyBlock().getLightEmission()` for the block's (sources read; Lib's `NeoForgeFluidLook.lightEmission`).
- Vanilla's flowing fluid sprites animate towards **+v** (each frame of `water_flow.png`/`lava_flow.png` is the previous one moved a pixel down), and `FluidRenderer` maps +v along the flow and draws the flowing sprite at half density (u/v 0 to 8 per block). So a quad shows fluid flowing along a direction when the sprite's +v runs along it (`ConduitUvs.flowTurns`) (measured from the client jar's textures; seen in a client on proto/tube-fx 2026-11-27).
- Quad light emission in a chunk-meshed model: the chunk path (`VertexConsumer.putBlockBakedQuad`, from `SectionCompiler`) lights each vertex with `instance.getLightCoordsWithEmission(vertex, quad.materialInfo().lightEmission())`, so the level goes in `BakedQuad.MaterialInfo.of(material, transparency, tintIndex, shade, lightEmission, ao)`. `ExtraFaceData(colour, lightEmission, ao)` only feeds it through the `FaceBakery.bakeQuad(ModelBaker, ...)` overload (max of both); the `Interner` overload a dynamic model calls takes the `MaterialInfo` as given. Per quad, not per pixel, and the block gives off no light (sources read; Lib's `ConduitQuad.lightEmission`). `MaterialInfo.of` reaches `Sheets` (registries), so it cannot run in a plain JUnit test: `Bootstrap.bootStrap()` there fails with "There is no current FML Loader" from `SharedConstants`.

## Codecs for untrusted settings (verified in the NeoForge and patched sources and by GameTests)

- `ItemResource.CODEC` refuses `minecraft:air` with a `DataResult` error, but an item whose component patch fails `ItemStack.validateStrict` (e.g. `minecraft:max_damage` on a stackable item: "Item cannot be both damageable and stackable") decodes **without an error** to `ItemResource.EMPTY`; `ItemResource.of(Holder, DataComponentPatch)` only logs a warning. A record whose constructor throws on an empty resource then throws `IllegalArgumentException` out of `codec.parse(...)`, as DFU does not catch exceptions from the constructor `RecordCodecBuilder` applies. Decode client input in a try/catch, or re-check for empty after decoding.
- `optionalFieldOf(name, default)` falls back to the default only when the field is missing; a present field that fails (a list over `listOf(0, max)`, a number outside `Codec.intRange`, a string for `Codec.BOOL`) fails the whole parse. `lenientOptionalFieldOf` (DataFixerUpper 9.0.19) is the one that swallows bad values.
- Sending a settings record as a `CompoundTag` (`ByteBufCodecs.COMPOUND_TAG`, encoded with the record's `MapCodec` through `registries.createSerializationContext(NbtOps.INSTANCE)`) lets the payload handler decode and refuse bad values; `ByteBufCodecs.fromCodecWithRegistries` would fail in the connection's decoder instead and disconnect the player.
- `TranslatableContents` reads `%%` in a lang string as a literal `%` (its format pattern is `%(?:(\d+)\$)?([A-Za-z%]|$)`), also for a string used without arguments, so "Bulk 50%" is written `"Bulk 50%%"`.

## Registry aliases and tag-conditioned recipes (facade move to Lib; verified in the NeoForge `26.1.x` sources and patches, by `runData` and the `facade_old_id_resolves` and `facade_recipe_binder` GameTests)

- Renaming a registry entry: `Registry#addAlias(Identifier from, Identifier to)` (NeoForge's `IRegistryExtension`,
  implemented in `BaseMappedRegistry`). The patched `MappedRegistry` lookups (`getValue`, `get`, `containsKey`,
  `getOrThrow`, holder lookups) run the name through `resolve`, which follows the alias only when `from` is not itself
  registered, so codecs reading an item id (saved `ItemStack`s) load the new item. Aliases are not saved; add them on
  every start. `RegisterEvent#getRegistry` is `@Nullable` for NullAway, so call `BuiltInRegistries.ITEM.addAlias(...)`
  inside the `RegisterEvent` for `Registries.ITEM`. `DeferredRegister#addAlias` also exists but
  must be called before `RegisterEvent` fires. An `Identifier` with an upper-case letter crashes registration.
- `neoforge:tag_empty` (`TagEmptyCondition`, default registry `minecraft:item`) works on recipes: recipe conditions see
  the tags being loaded in the same reload (`ConditionContext` from the pending tags). Two recipes with
  `tag_empty` and `neoforge:not` of it load exactly one (Lib's `facade` / `facade_from_ingot`).
  `RecipeOutput#withConditions(...)` writes the conditions in datagen.
- `RecipeManager#byKey(ResourceKey<Recipe<?>>)` on the server tells whether a conditional recipe loaded.

## Facades and mimicking blocks (verified in the patched and NeoForge sources and by the `facade_*` GameTests unless marked; rendering not yet seen in a client)

- `LevelChunk.setBlockState` drops the block entity (and calls `preRemoveSideEffects`) only when the block changes (`!oldState.is(newBlock)`); a state change of the same block keeps it and calls `blockEntity.setBlockState(state)`. It re-checks light when `LightEngine.hasDifferentLightProperties` says so. So a boolean block state property can mirror block entity data that vanilla caches per state (`facade_place_and_take` sees the same block entity after the flag flips).
- `Properties.noOcclusion()` sets `canOcclude` false for every state of the block, which empties the occlusion shape; there is no per-state way back. Light is per state regardless: override `getLightDampening(BlockState)` (15 = opaque) and `propagatesSkylightDown(BlockState)`; both are cached in `initCache`. With `dynamicShape()` the shape is not cached, and the default `isRedstoneConductor`, `isSuffocating` and `isViewBlocking` predicates test `isCollisionShapeFullBlock`, so a block whose shape becomes a full cube also conducts redstone and suffocates.
- `Facades.canMimic` uses `BlockState.isSolidRender()` (`canOcclude` and a full occlusion shape): true for stone and planks, false for glass, slabs and leaves; `hasBlockEntity()` rules out chests and furnaces.
- `ModelBlockRenderer.tesselateBlock` culls every part's culled faces against the rendered block's own state and its neighbours (`Block.shouldRenderFace`), and tints with `BlockColors.getTintSources(renderedState)`; only when that list is empty does it call NeoForge's `IClientBlockExtensions.collectDynamicTintValues(state, level, pos, IntList)` (register with `RegisterClientExtensionsEvent.registerBlock`), the hook for blocks that show another block's model. Quads with `tintIndex == -1` never ask. (Sources, compiled.)
- Another block's baked model can be composed into a `DynamicBlockStateModel`: `getBlockStateModelSet().get(facade).collectParts(level, pos, facade, random, output)`. NeoForge's `particleMaterial(BlockAndTintGetter, BlockPos, BlockState)` overload is what `BlockStateModelSet.getParticleMaterial(state, level, pos)` calls. `createGeometryKey` has no caller in vanilla or NeoForge 26.1.2; `CompositeBlockModel` returns null when a sub-model gives no key, and `SingleVariant` returns itself. (Sources, compiled.)
- `LevelRenderer.setSectionDirty(sectionX, sectionY, sectionZ)` is public (`Minecraft.levelRenderer`); `ChunkSource.getChunkNow(x, z)` gives a `@Nullable LevelChunk`, and `LevelChunk.getBlockEntities()` its block entity map. `ChunkPos` is a record (`x()`, `z()`). (Sources, compiled.)
- Item model types: `RegisterItemModelsEvent.register(Identifier, MapCodec<? extends ItemModel.Unbaked>)` (mod bus, client). `ItemModel.Unbaked` has `type()`, `resolveDependencies` and `bake(ItemModel.BakingContext, Matrix4fc)`; `context.missingItemModel(transformation)` is the missing model. `ItemModel.update(ItemStackRenderState, ItemStack, ItemModelResolver, ItemDisplayContext, @Nullable ClientLevel, @Nullable ItemOwner, int seed)` can draw another stack with `resolver.appendItemLayers(output, stack, context, level, owner, seed)`; call `output.appendModelIdentityElement(this)` first. Datagen: `itemModels.itemModelOutput.accept(item, unbaked)` writes `items/<id>.json` as `{"model": {"type": ...}}` (runData).
- Recipes: `RecipeSerializer` is a record `(MapCodec<T>, StreamCodec<RegistryFriendlyByteBuf, T>)`. `CustomRecipe` needs `matches(CraftingInput, Level)`, `assemble(CraftingInput)` (no registry argument any more) and `getSerializer()`; it is special (no recipe book, no unlock). `ItemStackTemplate(item, count).create()` makes the result stack; `ItemStackTemplate.CODEC` writes `{"id", "count"}`. Datagen: `SpecialRecipeBuilder.special(Supplier<Recipe<?>>).save(output, ResourceKey)`. A mod may have several `Registries.RECIPE_SERIALIZER` registrars. A crafting grid of one stone also matches vanilla's stone button recipe, so a test of "no recipe" must check the result item, not emptiness.
- Data components: a `BlockState` component is `persistent(BlockState.CODEC).networkSynchronized(ByteBufCodecs.idMapper(Block.BLOCK_STATE_REGISTRY))`. NeoForge registers `DATA_COMPONENT_TYPE` before blocks and items (`GameData.getRegistrationOrder`), so `Item.Properties.component(ourType.get(), value)` works in an item factory; a stack whose value equals the default saves no patch.
- `BuildCreativeModeTabContentsEvent` (mod bus): `insertAfter(existing, newStack, TabVisibility)` places extra stacks of the same item with other components next to the one the tab lists; they show in `tab.getDisplayItems()` when a test calls `tab.buildContents`.
- `BlockState.onDestroyedByPlayer(level, pos, player, tool, willHarvest, fluid)` (NeoForge) can be called from a GameTest with a mock player to test part-by-part breaking.

## Crafting in code (verified in the NeoForge 26.1.2.109 and patched sources and by the `crafting_*` GameTests)

- A crafting table recipe from code: `level.recipeAccess().getRecipeFor(RecipeType.CRAFTING, CraftingInput.of(3, 3, grid), level)` returns `Optional<RecipeHolder<CraftingRecipe>>`; `CraftingInput.of` trims empty rows and columns, so a shaped recipe placed anywhere in the 3 by 3 grid matches (sticks from planks in cells 0 and 3). `recipe.assemble(input)` gives the result and `getRemainingItems(input)` a `NonNullList` of remainders for the trimmed input. Nothing else is needed to craft outside a crafting table.
- `Transaction.open(TransactionContext parent)` opens a nested transaction; closing it without `commit()` puts back only what it did, so "take this input from the first option that has enough" is one nested transaction per option inside the run's root transaction.
- `ItemStackTemplate`'s codec caps `count` at 1 to 99 (`ExtraCodecs.intRange(1, 99)`) and its constructor throws `IllegalStateException` for air or count 0, so a pattern output (`ItemOutput`) above 99 can be built in memory but not saved; the encoding screen caps outputs at 64.
- Vanilla `Slot.mayPlace` returns true and does not ask `container.canPlaceItem`; a slot that should refuse what its container refuses overrides `mayPlace` to call `container.canPlaceItem(getContainerSlot(), stack)`. A number-key `SWAP` click checks `target.mayPlace(source)` before moving the hotbar stack in. `SimpleContainer.canPlaceItem` accepts anything, so a client menu that must predict a refusal needs its own container subclass.
- `Inventory.findSlotMatchingItem(stack)` matches with `ItemStack.isSameItemSameComponents`, so it does not find a stack of the same item that carries a data component (a configured module); loop and test `is(item)` instead.

## Tags naming missing entries, and convention tags (verified by `runGameTestServer` and the NeoForge `26.1.x` sources)

- A tag file whose (non-optional) entry names an id that is not registered fails to load as a whole, not just that entry: a generated `minecraft:mineable/pickaxe` still naming a machine tier that was removed dropped every block from the tag, so `content_index_tags`, mining speed and mineable checks of unrelated areas failed, and an advancement whose criterion named the missing item did not load. After changing which tiers or blocks a definition registers, re-run `runData` before the GameTests.
- NeoForge's `Tags.Items` has `ENDER_PEARLS` and `NETHER_STARS` but no tag for the eye of ender; a mod that needs one puts `Items.ENDER_EYE` in its own tag with `tag(key).add(...)` in its item tags provider.

## Datagen (verified with `:storage:neoforge:runData`)

- `runData` is a `clientData` run and fires `GatherDataEvent.Client`; subscribe with `@EventBusSubscriber(modid = ..., value = Dist.CLIENT)` and register providers with `event.createProvider(...)` (`PackOutput` or `(PackOutput, CompletableFuture<HolderLookup.Provider>)` factories).
- Models: extend `ModelProvider(PackOutput, modId)` and override `registerModels(BlockModelGenerators, ItemModelGenerators)`. By default it validates every block and item in the mod's namespace; a block without an item is fine. Custom elements via NeoForge's `ExtendedModelTemplateBuilder.builder().requiredTextureSlot(...).element(e -> e.from(..).to(..).textureAll(slot)).build().create(block, mapping, blockModels.modelOutput)`, then `blockModels.blockStateOutput.accept(BlockModelGenerators.createSimpleBlock(block, BlockModelGenerators.plainVariant(model)))`.

- Lang: NeoForge `LanguageProvider(PackOutput, modId, "en_us")`, `addTranslations()`, `add(key, value)`, `addBlock(Supplier<Block>, name)`.
- Advancements: `event.createProvider((output, registries) -> new AdvancementProvider(output, registries, List.of(subProvider)))` with vanilla's `net.minecraft.data.advancements.AdvancementProvider` and an `AdvancementSubProvider` (`generate(HolderLookup.Provider, Consumer<AdvancementHolder>)`). `Advancement.Builder.advancement().parent(AdvancementHolder).display(ItemLike icon, Component title, Component description, @Nullable Identifier background, AdvancementType, showToast, announceChat, hidden).addCriterion(name, criterion).save(output, "ns:path")`; the background is a texture id without `textures/` and `.png`, e.g. `minecraft:gui/advancements/backgrounds/stone`, stored as `ClientAsset.ResourceTexture`. `InventoryChangeTrigger.TriggerInstance.hasItems(ItemPredicate...)` needs every predicate matched, so "any of these items" is one predicate: `ItemPredicate.Builder.item().of(items, ItemLike...)` or `.of(items, tag)`.
- Custom criteria: extend `SimpleCriterionTrigger<T>` with `codec()` and a record `T implements SimpleCriterionTrigger.SimpleInstance` whose codec has `EntityPredicate.ADVANCEMENT_CODEC.optionalFieldOf("player")`; fire with the protected `trigger(ServerPlayer, Predicate<T>)`; register the trigger in `Registries.TRIGGER_TYPE` through an ordinary registrar; `trigger.createCriterion(instance)` makes the datagen criterion. Vanilla fires the beacon's for the `ServerPlayer`s in `new AABB(pos).inflate(10, 5, 10)`.
- Loot: `new LootTableProvider(output, Set.of(), List.of(new LootTableProvider.SubProviderEntry(MyBlockLoot::new, LootContextParamSets.BLOCK)), registries)`; `BlockLootSubProvider(Set.of(), FeatureFlags.DEFAULT_FLAGS, registries)` with `generate()` and `getKnownBlocks()`.
- Output goes to `common/src/generated/resources`; the `.cache` folder there is gitignored.
- `ModelProvider.getKnownBlocks()` / `getKnownItems()` (NeoForge additions, protected) decide which blocks must get a blockstate; the default is every block in the mod's namespace.
- Custom block state model in datagen: `blockStateOutput.accept(MultiVariantGenerator.dispatch(block, MultiVariant.of(new CustomBlockStateModelBuilder.Simple(unbaked))))` writes `{"variants": {"": {"type": "<id>", ...codec fields}}}`. Encoding needs the codec registered, which works because `RegisterBlockStateModels` fires in `ClientHooks.initClientRegistries()`, also called at datagen startup (`client/data/Main` patch).
- Items without an explicit model: `ModelProvider` gives every known `BlockItem` a plain model pointing at its block model (`ItemInfoCollector.finalizeAndValidate`); any other known item without one fails with "Missing item model definitions". Override `getKnownItems()` like `getKnownBlocks()` when the GameTest source set registers items in the namespace.
- Tinted flat item: `ModelTemplates.FLAT_ITEM.create(ModelLocationUtils.getModelLocation(item), TextureMapping.layer0(new Material(texture)), itemModels.modelOutput)`, then `itemModels.itemModelOutput.accept(item, ItemModelUtils.tintedModel(model, ItemModelUtils.constantTint(rgb)))`; `Constant` makes the colour opaque itself. Cubes: `ModelTemplates.CUBE_ALL.create(block, TextureMapping.cube(new Material(texture)), blockModels.modelOutput)` plus `BlockModelGenerators.createSimpleBlock(block, BlockModelGenerators.plainVariant(model))`.
- The tinted item definition it writes is `{"model": {"type": "minecraft:model", "model": "<model id>", "tints": [{"type": "minecraft:constant", "value": <int>}]}}`, with the colour as a signed ARGB int (`0xDCDCDC` becomes `-2302756`). One shared flat model per form (`<modid>:item/material/dust`) with a per-item constant tint is enough; the model only needs to be created once.
- `DataGenerator` throws "Duplicate provider: <name>" when two providers share `getName()`. `ModelProvider` is named `"Model Definitions - <modid>"` and `TagsProvider` `"Tags for <registry> mod id <modid>"`, so a second model or item-tag provider for the same mod must override `getName()`. A language file has exactly one provider per locale.
- `ModelProvider`'s model output (`SimpleModelCollector.accept`) throws "Duplicate model definition for <id>" when a model id is written twice, and the item model output throws "Duplicate item model definition"; a model shared by several items (a material form's flat model) must be created once, which `ContentDatagen` tracks per run (patched `ModelProvider` sources).
- `SimpleCookingRecipeBuilder.smelting` / `blasting(Ingredient, RecipeCategory, CookingBookCategory, ItemLike, float, int)` are public statics that need no provider, so cooking recipes can be declared in common with the ingredient from `Ingredient.of(items.getOrThrow(tag))`; the output is byte-identical to the provider version.
- `GatherDataEvent.DataProviderFromOutput<T>` and `DataProviderFromOutputLookup<T>` are public nested functional interfaces, so a helper can take provider factories (`Foo::new`) as parameters and hand them to `event.createProvider` later. NeoForge's `LanguageProvider.add(String, String)` and `add(Block|Item, String)` are public, and `run` writes nothing when no line was added. A `LootTableProvider` whose sub-providers produce no tables writes no files.
- `RecipeProvider.has(ItemLike)` is `inventoryTrigger(ItemPredicate.Builder.item().of(items, item))`; outside a provider, `InventoryChangeTrigger.TriggerInstance.hasItems(ItemPredicate.Builder.item().of(items, item))` builds the same criterion (`ItemPredicate.Builder.of(HolderGetter<Item>, ItemLike...)`). `ModelTemplates.CUBE_ORIENTABLE` with `FRONT`, `SIDE` and `TOP` plus `BlockModelGenerators.ROTATION_HORIZONTAL_FACING`, and `createSimpleBlock(block, variant)` in place of `MultiVariantGenerator.dispatch(block, variant)`, give the same files.
- NeoForge's `TagsProvider` only checks that entries in its own mod's namespace exist ("Assume tags from other namespaces always exists"), so `tag(c:dusts).addTag(c:dusts/tin)` needs no other provider; the written file has no `replace` key (it defaults to false) and merges with NeoForge's own `c:dusts`.
- Cooking recipes: `SimpleCookingRecipeBuilder.smelting|blasting(Ingredient, RecipeCategory, CookingBookCategory, ItemLike result, float xp, int ticks)`, then `.unlockedBy(...)` and `.save(output, ResourceKey<Recipe<?>>)` (the key form lets a `maxtech:` recipe produce a vanilla item). A tag ingredient inside a `RecipeProvider` is `Ingredient.of(items.getOrThrow(tagKey))` (`items` is the protected `HolderGetter<Item>`). Verified by `material_tin_smelting`.
- Untinted flat item with a borrowed texture: `ModelTemplates.FLAT_ITEM.create(ModelLocationUtils.getModelLocation(item), TextureMapping.layer0(new Material(texture)), itemModels.modelOutput)`, then `itemModels.itemModelOutput.accept(item, ItemModelUtils.plainModel(model))`.
- A block model with a colour baked into its quads: `ExtendedModelTemplateBuilder.builder().parent(Identifier.withDefaultNamespace("block/block")).requiredTextureSlot(TextureSlot.ALL).requiredTextureSlot(TextureSlot.PARTICLE).element(e -> e.from(0, 0, 0).to(16, 16, 16).allFaces((side, face) -> face.texture(TextureSlot.ALL).cullface(side).color(argb))).build().create(modelId, TextureMapping.cube(new Material(texture)), blockModels.modelOutput)` writes `"neoforge_data": {"color": "ffrrggbb"}` per face (ARGB; set the alpha). `ElementBuilder.color` also exists but writes element-level data; per face is explicit.
- A block model that only inherits another model: `new ModelTemplate(Optional.of(parentModel), Optional.empty()).create(block, new TextureMapping(), blockModels.modelOutput)` writes `{"parent": "<parent>"}` at the block's model location; the public constructor is `ModelTemplate(Optional<Identifier> parent, Optional<String> suffix, TextureSlot... requiredSlots)`. `getKnownBlocks()`/`getKnownItems()` can return `BuiltInRegistries.BLOCK.wrapAsHolder(block)` for blocks that have no `RegistryEntry` at hand.
- Block tags: NeoForge `BlockTagsProvider(PackOutput, CompletableFuture<HolderLookup.Provider>, modId)`, override `addTags(HolderLookup.Provider)` and use `tag(BlockTags.X).add(block)`; register with `event.createProvider(MyTags::new)`.
- Data maps: extend NeoForge `DataMapProvider(PackOutput, CompletableFuture<HolderLookup.Provider>)`, implement `gather(HolderLookup.Provider)` with `builder(NeoForgeDataMaps.FURNACE_FUELS).add(Holder<Item>, new FurnaceFuel(ticks), false)` (also `add(TagKey, ...)`); it writes `data/neoforge/data_maps/item/furnace_fuels.json` as `{"values": {"<item>": {"burn_time": n}}}`, which merges with other packs' entries.
- Item tags: NeoForge `ItemTagsProvider(PackOutput, CompletableFuture<HolderLookup.Provider>, modId)` (no block-tag lookup argument any more), same `addTags` and `tag(key).add(item)`; output lands in `data/<tag namespace>/tags/item/...`. `RecipeCategory.TOOLS` is written as `"category": "equipment"`.
- `ShapelessRecipeBuilder.requires` has `(TagKey)`, `(ItemLike[, count])` and `(Ingredient[, count])` but no tag-with-count overload; use `requires(Ingredient.of(items.getOrThrow(tag)), count)`, which writes the tag `count` times. `ShapelessRecipeBuilder.shapeless(items, category, result, count)` is the static entry point outside the provider helpers.
- `TextureMapping.column(Material side, Material end)` fills only `SIDE` and `END`; add `.copySlot(TextureSlot.SIDE, TextureSlot.PARTICLE)` when the template requires a particle slot.
- Recipes: extend `RecipeProvider(HolderLookup.Provider, RecipeOutput)` and implement `buildRecipes()` with the protected helpers `shaped(category, item[, count])`, `shapeless(...)`, `has(TagKey)`, then `.save(output)` (id = result item id). Datagen runs it through a subclass of `RecipeProvider.Runner(PackOutput, CompletableFuture<HolderLookup.Provider>)` implementing `createRecipeProvider(registries, output)` and `getName()`; `event.createProvider(MyRecipes.Runner::new)`.
- Which datagen classes `common` may reference: the dedicated server jar (`minecraft_26.1.2_server.jar` in `~/.gradle/caches/neoformruntime/artifacts/` is a bundler; the game is `META-INF/versions/26.1.2/server-26.1.2.jar` inside it) ships `net.minecraft.data.*` (`recipes.RecipeProvider`, `ShapedRecipeBuilder`, `RecipeOutput`, `loot.BlockLootSubProvider`, `tags.TagsProvider`) but no `net.minecraft.client.*` class at all. So recipe and loot builder types are safe in classes a server loads, while the model generators (`net.minecraft.client.data.models.*`, `Material`, and NeoForge's `ExtendedModelTemplateBuilder`/`CustomBlockStateModelBuilder`) are not, not even as a lambda's parameter type in a static initialiser: creating the lambda resolves its method type. The content builder therefore declares models as plain data and the `neoforge` project interprets them (verified by listing the jars; the lambda rule is JVM behaviour, not tried on a server).
- Recipes outside a `RecipeProvider` subclass: `ShapedRecipeBuilder.shaped(HolderGetter<Item>, category, item[, count])` and `ShapelessRecipeBuilder.shapeless(items, category, item[, count])` are public statics (the provider's `shaped`/`shapeless` just call them with its `items`), and `InventoryChangeTrigger.TriggerInstance.hasItems(ItemPredicate.Builder.item().of(items, tag))` builds the same criterion as the provider's `has(TagKey)`.
- NeoForge's `LanguageProvider` keeps entries in a `TreeMap`, so the order of `add` calls never shows in `en_us.json`; tag files, by contrast, list entries in the order they were added.
- Vanilla item textures in 26.1.2 (listed from `minecraft_26.1.2_client.jar` in `~/.gradle/caches/neoformruntime/artifacts/`): the chain is `item/iron_chain` (no `item/chain`), and the tripwire hook has no item texture (its item model uses the block texture). `unzip -l` on that jar settles whether a texture exists before a model names it.
- A machine recipe's `fluidInput(Tags.Fluids.WATER, mb)` writes `"fluid": "#c:water"`, which NeoForge's own data fills with vanilla water, so a GameTest filling a tank with `Fluids.WATER` matches it (verified by `forming_cutter_needs_water`).
- Re-running a recipe provider into another output: `RecipeOutput` is `accept(ResourceKey<Recipe<?>>, Recipe<?>, @Nullable AdvancementHolder, ICondition...)` (abstract, from NeoForge's `IRecipeOutputExtension`; the three-argument `accept` defaults to it), `advancement()` and `includeRootAdvancement()`, so a record implementing those three can filter or rewrite every recipe a provider saves, builder or direct `accept` alike. `RecipeProvider` keeps `registries`, `items` and `output` as `protected final` fields and `buildRecipes()` is `protected`, so a provider in the same package can construct another and call its `buildRecipes()` with the wrapping output; delegate `advancement()` to the real output, since cooking and crafting builders build their unlock advancement from it.
- Layered flat items: `ModelTemplates.createItem("generated", slots...)` with `TextureSlot.LAYER0..LAYER2` and `TextureSlot.create("layer3")`/`("layer4")`; vanilla's `ItemModelGenerator.LAYERS` reads `layer0` to `layer4`. The item definition's `tints` list is indexed by layer (each generated layer's quads get `tintIndex` = its layer index), and `ItemFeatureRenderer.getLayerColorSafe` draws an index past the list's end untinted (-1), so a list that stops at the last tinted layer leaves the overlays above it white; an untinted layer below a tinted one needs `constantTint(0xFFFFFF)`.
- Whether a texture exists, in datagen: `GatherDataEvent.getResourceManager(PackType.CLIENT_RESOURCES).getResource(Identifier.withPath("textures/<path>.png"))`.
- An element with only some faces: `ElementBuilder.face(Direction, Consumer<FaceBuilder>)` adds one face (`allFaces` adds all six), so per-face overlays are elements holding just the faces that have that layer; each needs its own `TextureSlot.create(name)` in the template's required slots and the mapping.
- `GatherDataEvent.createProvider(...)` returns the provider it created, so a provider can be handed more before the run (for example the client resource manager).

- `runData` keeps a hash cache in `<output>/.cache` (gitignored) and skips writing files it believes unchanged, so a hand-edited generated file survives a local `runData`. Delete the `.cache` directory to force a full rewrite; CI does that before checking that generated files match (verified locally with a deliberately stale `en_us.json`).
- Generated tag files and advancement item lists keep insertion order, not sorted order: `TagsProvider` writes a tag's `values` in the order `add` was called, and `ItemPredicate.Builder.item().of(HolderGetter<Item>, ItemLike...)` lists the items as given. With the content builder that is declaration order, which is the order the registering classes load in, so moving an entry to a class that loads earlier or later reorders `mineable/pickaxe.json` and similar files. Lang files are sorted by key and unaffected.
- `DataGenerator.Cached.run` runs a generator's providers one after another in the order they were added (`providersToRun` is a `LinkedHashMap`; each `provider.run(...)` is joined before the next starts), and NeoForge gives each mod of a `runData` its own generator. So a provider a mod's `GatherDataEvent` handler adds last runs after all of that mod's others, and `event.getGenerator().getProvidersView()` lists them (patched sources; `ContentIndexProvider`).
- `event.createProvider(DataProviderFromOutputLookup)` passes `getLookupProvider()` as it is at that call; `createDatapackRegistryObjects` replaces it with one that includes the new datapack entries. A provider that must see them is added after that call.
- `HashCache` deletes files no provider wrote this run only in `purgeStaleAndWrite`, after every provider has run, so a provider reading generated files from disk still sees the files of a recipe or tag that was just removed. `RecipeProvider.Runner` and `TagsProvider` can be run a second time into another `CachedOutput` instead (a lambda-sized interface: `writeIfNeeded(Path, byte[], HashCode)`): the runner builds a new recipe provider and recipe set per run, and `TagsProvider.createContentsProvider` clears its builders before `addTags` (patched sources; verified by `ContentIndexProvider`, whose second run left every other generated file byte-identical).
- A crafting recipe's JSON also has a `category` (its recipe book tab: `building`, `misc`, `equipment`, `redstone`); only `maxtech_lib:machine` recipes' `category` is a machine recipe category. The top-level `type` is the recipe serializer's id (`Recipe.CODEC` dispatches on `RECIPE_SERIALIZER`), so `BuiltInRegistries.RECIPE_SERIALIZER.getKey(recipe.getSerializer())` gives it back for a loaded recipe (`content_index_recipes`).
- Conditional recipes for an optional mod: `output.withConditions(new ModLoadedCondition("guideme"))` (NeoForge `IRecipeOutputExtension.withConditions(ICondition...)`, `common.conditions.ModLoadedCondition(String modid)` record) wraps a `RecipeOutput`; recipes saved through it get `"neoforge:conditions": [{"type": "neoforge:mod_loaded", "modid": ...}]` at the top, and so do their recipe-unlock advancements. A recipe may name another mod's tags by id (`TagKey.create(Registries.ITEM, Identifier.fromNamespaceAndPath("<othermod>", ...))`) in datagen while that mod is not loaded; nothing checks them. `ShapedRecipeBuilder.save(output, ResourceKey<Recipe<?>>)` gives a second recipe for the same result its own id (verified with `runData`).
- On a server where the condition fails, the recipe does not load, but its file is still readable through `server.getResourceManager().getResource(Identifier "<ns>:recipe/<path>.json")`, so a GameTest can check the condition is there (`recipes_compat_conditional`). Such a recipe would not load without the condition either when its tags are the missing mod's (no pack defines them), so a "did not load" check alone cannot tell whether the condition exists.
- Shaped recipes also match their mirror image (`ShapedRecipePattern.matches` tries the x-flipped grid unless the pattern is symmetrical), so two one-row recipes `hPw` and `wPh` with the same ingredients collide, so give such recipes two rows (patched sources).
- `RecipeBuilder.save(output)` names the recipe after its result (`getDefaultRecipeId`: the item's own id), so an addon that saves a recipe for another mod's item without a key writes `data/<that mod>/recipe/<item>.json` and replaces that mod's recipe of the same id; pass a `ResourceKey` in the addon's namespace. `RecipeCategory.TOOLS` writes `"category": "equipment"` and puts the unlock advancement under `advancement/recipes/tools/`.

## Generated guide tables and preset checks (verified by `runData` and GameTests)

- GuideME has no include or fragment tag (re-checked in the 26.1.14-beta sources: `DefaultExtensions`, `PageCompiler`), so a page cannot embed a generated snippet. A page with generated tables is written by datagen instead: the hand-written source holds `<!-- generated:name -->` lines and `GuideTemplateProvider` writes the finished page into `src/generated`. The source is never rewritten, so a re-run changes nothing and CI's generated-folder diff covers the numbers.
- A marker cannot stay in a shipped page: `<!-- ... -->` is a PARSING ERROR in `PageCompiler` (MDX), and `{/* */}` and `[//]: # (...)` parse but `PageCompiler.compileBlockContext` turns any node type it does not handle into a visible error block ("Unhandled Markdown node in block context") that `GuidePageCheck` does not report.
- `PackOutput.getOutputFolder()` is the mod's generated resources root (`<mod>/common/src/generated/resources`); `Path.getParent()` is `@Nullable` for NullAway, so resolve `../../guide` and `normalize()` instead of chaining `getParent()`.
- `GatherDataEvent.getLookupProvider()` (what `createProvider((output, lookup) -> ...)` passes) holds the entries of `createDatapackRegistryObjects` only for providers created after that call; before it, `lookupOrThrow` of a modded datapack registry fails with "Registry ... not found".
- `ConfigFile.paths()` returns every declared path as soon as the file is registered, before any config loads, so a GameTest can compare a spec with its preset JSON (`PresetConfig.presetProblems()`). Presets are layered on `standalone`, so `pack.json` may leave a path out; only `standalone.json` must name every path.
- `RodStats.all()` is built with `Map.copyOf`, whose iteration order differs between JVM runs; sort before writing it into generated output.

# Config

## Config load order, recipe conditions, creative tabs and JEI hiding (verified in the NeoForge sources on `26.1.x`, the JEI 29.43.0.106 API sources and by the `content_toggle_*` GameTests)

- **SERVER config loads too late for recipe conditions.** `ServerLifecycleHooks.handleServerAboutToStart` loads SERVER configs (called from the patched `DedicatedServer`, `IntegratedServer` and `GameTestServer` init), after `WorldLoader` has already loaded the datapacks and recipes. COMMON (and CLIENT, on the client) configs load in `CommonModLoader`'s "Config loading" init task at startup, so a switch that gates recipes, creative tabs and JEI must be COMMON. That task is skipped in datagen (`if (!datagen)`), so a COMMON value read during `runData` throws `IllegalStateException`. `ModConfig.Type` also has `STARTUP` (loaded on registration, not synced).
- **Custom recipe conditions**: implement `common.conditions.ICondition` (`boolean test(IContext)`, `MapCodec<? extends ICondition> codec()`) and register the `MapCodec` in `NeoForgeRegistries.Keys.CONDITION_CODECS`; a `Platform.registry().<MapCodec<? extends ICondition>>registrar(modId, NeoForgeRegistries.Keys.CONDITION_CODECS)` entry works (`lib.neoforge.ContentEnabledCondition`, type `maxtech_lib:content_enabled`). A recipe JSON lists them under `"neoforge:conditions"`; `ICondition.conditionsMatched(JsonOps.INSTANCE, json)` evaluates that block, handy in tests. A GameTest-resources recipe whose condition is false is absent from `level.recipeAccess().byKey(...)`.
- **`BuildCreativeModeTabContentsEvent` reaches every mod for every tab**: `EventHooks` posts it through `ModLoader.postEvent`, so one listener on one mod's bus sees vanilla's and other mods' tabs, after the tab's own `displayItems` ran. `removeIf(Predicate<? super ItemStack>, TabVisibility.PARENT_AND_SEARCH_TABS)` removes entries from the tab and the search tab; `tab.getSearchTabDisplayItems()` returns the search entries after `buildContents`.
- **JEI hiding**: `IModPlugin.onRuntimeAvailable(IJeiRuntime)` runs each time JEI starts; `runtime.getIngredientManager().removeIngredientsAtRuntime(VanillaTypes.ITEM_STACK, Collection<ItemStack>)` hides stacks (verified in the API sources and by compiling; not yet seen in a running client).
- Error Prone's `ReferenceEquality` flags `==` on a non-final class or an interface that could define `equals`; making `ItemPipeContents` non-final turned existing identity checks into build errors, fixed with a justified `@SuppressWarnings("ReferenceEquality")` at each site. A class permitted by a `sealed` interface that becomes non-final must be declared `non-sealed`.

## NeoForge's config screen (B09 item 20; verified in the NeoForge 26.1.2.109 and FML 11.0.15 sources, by compiling, `runData` and the `config_lang_complete` GameTests; the screen is not yet seen in a running client)

- **Registering:** `container.registerExtensionPoint(IConfigScreenFactory.class, (mod, parent) -> new ConfigurationScreen(mod, parent))` from the client `@Mod` class; FML injects a `ModContainer` constructor parameter (`FMLModContainer` allows `IEventBus`, `ModContainer`, `FMLModContainer`, `Dist`). The screen lists every config file of the mod (`ModConfigs.getConfigSet(type)`); a SERVER file is editable only in singleplayer while not open to LAN, and greyed out while its spec is not loaded (outside a world).
- **Lang keys:** a value's name is `ValueSpec.getTranslationKey()`, a section's `spec.getLevelTranslationKey(path)` (set by `builder.translation(key)` before `define`/`push`); without one the screen falls back to `<modid>.configuration.<last path segment>`, which repeats across sections. The tooltip is `<key>.tooltip`, else the comment; the range line (`Range: ...`) shows only when the tooltip is translated. The default is not shown by NeoForge.
- **Comments:** `defineInRange` appends ` Default: <v>` and ` Range: <r>` lines to the comment and `defineEnum` an `Allowed Values: ...` line; `ValueSpec.getComment()` includes them. Section comments are `spec.getLevelComment(path)`.
- **Restart marks:** `builder.worldRestart()`/`gameRestart()` before a define set `ValueSpec.restartType()`; the screen offers to leave the world or quit after such a change. `GAME` is refused for SERVER configs (`validateSpec` throws). They also change caching: `ConfigValue.get()` caches, `set(v)` updates the cache only for `NONE`, and reloads (`afterReload`) clear only `NONE` caches; `WORLD` caches are cleared when a world closes. `ConfigValue.clearCache()` is public, so code that sets a marked value and wants it now clears the cache (Lib's `ConfigFile.set` does).
- **Ordering and extras:** entries show in declaration order (the values config is a `LinkedHashMap`). `ConfigurationScreen`'s third constructor takes a `Function4<ConfigurationScreen, ModConfig.Type, ModConfig, Component, Screen>` for the file's top screen; `ConfigurationSectionScreen.Context` is a public record (canonical constructor marked `@ApiStatus.Internal`), so a subclass can be built over `Context.top(...)` with reordered `entries`. Sub-sections are created in `createSection` with the base class, so a subclass that changes every level overrides it too (`lib.neoforge.client.ConfigScreens`).
- **Recheck on every NeoForge bump:** `ConfigScreens` copies NeoForge's private section-button keys
  (`neoforge.configuration.uitext.section`, `.sectiontext`) and the body of `createSection`, and builds the internal
  `Context` record; compare them with the new `ConfigurationScreen` before bumping.
- **Walking a mod's specs:** `ModConfigs.getModConfigs(modId)` lists them; CLIENT and COMMON specs are registered on a dedicated or GameTest server too, so a server-side test sees every file (`ConfigTranslations`).

## Config files per mod and recipe fallbacks (verified in the FML 11.0.15 sources and by `runData`)

- **One config file cannot hold several mods' keys.** `ConfigTracker.registerConfig(type, spec, container)` names the file `<modid>-<type>.toml` (`defaultConfigName`); the overload with a `fileName` exists, but `trackConfig` throws `RuntimeException("Detected config file conflict on <file> ...")` when a second `ModConfig` registers a file name already tracked. The suite's content switches therefore sit under `[modules]` in each mod's own common config.

# Client: models, rendering and screens

## Client models and rendering (verified in the NeoForge sources, patches and patched Minecraft sources; not yet seen in a running client)
- Chunk layer per quad: 26.1.2 has no `render_type` to set for cutout overlays. `FaceBakery.bakeQuad` computes the quad's `Transparency` from the sprite pixels inside the face's UVs (`SpriteContents.computeTransparency`), and `ChunkSectionLayer.byTransparency` puts it in the solid, cutout or translucent layer; item layers use the whole sprite's `transparency()`.

- Block state model types: `CustomUnbakedBlockStateModel` (`codec()`, `resolveDependencies`, `bake(ModelBaker)` returning a `BlockStateModel`), registered on the mod bus with `RegisterBlockStateModels.registerModel(Identifier, MapCodec)`. The baked side implements `DynamicBlockStateModel` and overrides `collectParts(BlockAndTintGetter, BlockPos, BlockState, RandomSource, List<BlockStateModelPart>)`, `particleMaterial()`, `materialFlags()` and optionally `createGeometryKey(...)` (must return non-null when overridden; value-equal keys mean identical geometry).
- `collectParts` runs on meshing threads. Read block entity data only through `level.getModelData(pos).get(ModelProperty)` (`ModelData.get` is `@Nullable`); `RenderSectionRegion` serves a per-section `ModelData` snapshot taken on the main thread. `SectionCopy` also copies the chunk's block entity map with `ImmutableMap.copyOf`, but the block entities themselves are live.
- Model data: override `getModelData()` on the block entity (called on the client main thread when a refresh was requested) and call `requestModelDataUpdate()` (client only, main thread only; `ModelDataManager.requestRefresh` throws off-thread). `onLoad()` requests one by default.
- A `ClientboundBlockEntityDataPacket` only calls `onDataPacket` (-> `loadAdditional`); it does not re-mesh the section, and neither does a block update whose state is unchanged. After changing render data on the client, call `requestModelDataUpdate()` and `level.sendBlockUpdated(pos, state, state, flags)` (on `ClientLevel` that is `LevelRenderer.blockChanged`, flag 8 = rebuild immediately).
- `ModelBaker.materials().get(new Material(Identifier), ModelDebugName)` gives a `Material.Baked` (sprite + forceTranslucent); `ModelDebugName` is a functional interface. `SimpleModelWrapper(QuadCollection, boolean useAO, Material.Baked particle)` is a public record implementing `BlockStateModelPart`. `QuadCollection.Builder` has `addCulledFace(Direction, quad)` and `addUnculledFace(quad)`.
- `FaceBakery.bakeQuad(ModelBaker.Interner, Vector3fc from, Vector3fc to, CuboidFace.UVs, Quadrant, BakedQuad.MaterialInfo, Direction, ModelState, @Nullable CuboidRotation, ExtraFaceData)` is public and static; `from`/`to` are in pixels (0 to 16); `FaceBakery.defaultFaceUV(from, to, facing)` gives the element-style UVs. `ModelBaker.Interner` only has `vector` and `materialInfo` abstract (`normals`/`colors` default to identity), so an identity interner works outside baking. `BlockModelRotation.IDENTITY` is the identity `ModelState`. `BakedQuad.MaterialInfo.of(Material.Baked, Transparency, tintIndex, shade, lightEmission, ambientOcclusion)`; `Transparency.NONE` puts it in the solid layer.
- `BakedQuad` carries NeoForge `BakedColors` (ARGB, per quad or per vertex), set from `ExtraFaceData(color, lightEmission, ambientOcclusion)` by `FaceBakery`. `VertexConsumer.putBlockBakedQuad` (the chunk path from `SectionCompiler`) and `putBakedQuad` multiply it into the vertex colour, so a tint can be baked into the quad without a block colour handler.
- Block colours are `RegisterColorHandlersEvent.BlockTintSources.register(List<BlockTintSource>, Block...)`: one tint source per tint index. Only quads with `tintIndex != -1` consult them.
- Level rendering is extract, then submit (the builder guide, `GuideGhosts`; compiled, not yet seen in a client). `ExtractLevelRenderStateEvent` (game bus, every frame, after vanilla's extraction) hands out the `LevelRenderState`; store your own data with `setRenderData(ContextKey<T>, T)` (`new ContextKey<>(Identifier)`), read it back with the `@Nullable getRenderData(key)`. `LevelRenderer.renderLevel` ends with `levelRenderState.reset()`, which clears render data (`resetRenderData()`), so each frame's extraction starts empty and nothing needs removing. `SubmitCustomGeometryEvent` (game bus) fires after block entities, particles and the block breaking animation are submitted and before the solid feature pass; `getSubmitNodeCollector().submitCustomGeometry(poseStack, RenderType, SubmitNodeCollector.CustomGeometryRenderer)` copies the pose at submission and later calls `render(PoseStack.Pose, VertexConsumer)` in the solid or the translucent feature pass, by `renderType.hasBlending()`, with one buffer per render type. The event's `getPoseStack()` has the camera at the origin: translate by `pos - getLevelRenderState().cameraRenderState.pos`. `RenderLevelStageEvent` has no stage enum any more, only subclasses (`AfterSky`, `AfterOpaqueBlocks`, `AfterOpaqueFeatures`, `AfterTranslucentFeatures`, `AfterTranslucentBlocks`, `AfterTranslucentParticles`, `AfterWeather`, `AfterLevel`); NeoForge's own javadoc sends geometry to `SubmitCustomGeometryEvent` instead.
- Ghost (see-through) blocks: `RenderTypes.translucentMovingBlock()` (block atlas, lightmap, blending, sorted on upload; the piston's type for moving translucent blocks). `VertexConsumer.putBakedQuad(PoseStack.Pose, BakedQuad, QuadInstance)` multiplies the instance colour (ARGB, alpha included) with the quad's NeoForge baked colour; `QuadInstance` has `setColor(argb)`, `setLightCoords` (`LightCoordsUtil.FULL_BRIGHT`) and `setOverlayCoords` (`OverlayTexture.NO_OVERLAY`). A block state's model: `Minecraft.getInstance().getModelManager().getBlockStateModelSet().get(state)`, a `BlockStateModel` whose NeoForge `collectParts(net.minecraft.client.renderer.block.BlockAndTintGetter, BlockPos, BlockState, RandomSource, List<BlockStateModelPart>)` fills parts (`BlockAndTintGetter.EMPTY` exists; the random-only overload is deprecated); `part.getQuads(@Nullable Direction)`. `BakedQuad` lives in `net.minecraft.client.resources.model.geometry`. A resource reload makes a new `BlockStateModelSet`, so cached quads are stale once it changes identity.
- Line geometry for `RenderTypes.lines()`: each vertex needs `addVertex(pose, x, y, z).setColor(argb).setNormal(pose, nx, ny, nz).setLineWidth(width)`, two vertices per edge; `ShapeRenderer.renderShape(poseStack, buffer, VoxelShape, x, y, z, argb, width)` does it for a shape.
- There is no client-side block change event in NeoForge 26.1.2: the `ClientLevel` patch posts only level load, entity and sound events, and `LevelRenderer.blockChanged` fires nothing. Client code that must follow blocks re-reads them (the builder guide does so each `ClientTickEvent.Post`, game bus, only while a guide is held).
- Client action bar: `Minecraft.getInstance().gui.setOverlayMessage(Component, boolean animate)`; it shows for 60 ticks. `Minecraft.hitResult` is a public `@Nullable HitResult`.
- Selection outline: `ExtractBlockOutlineRenderStateEvent` (game bus, cancellable) fires before vanilla computes the shape; `addCustomRenderer(CustomBlockOutlineRenderer)` adds a renderer whose `render(BlockOutlineRenderState, BufferSource, PoseStack, boolean translucentPass, LevelRenderState)` returns true to suppress vanilla's outline. It is called in both the opaque and translucent pass; vanilla draws only when `state.isTranslucent() == translucentPass`. Vanilla draws with `ShapeRenderer.renderShape(poseStack, buffer.getBuffer(RenderTypes.lines()), shape, pos - camera, ARGB.black(102) or 0xFF57FFE1 for high contrast, windowRenderState.appropriateLineWidth)` plus a `RenderTypes.secondaryBlockOutline()` pass at 0xFF000000, width 7 for high contrast; the camera is `levelRenderState.cameraRenderState.pos` and the width `Minecraft.getInstance().gameRenderer.getGameRenderState().windowRenderState.appropriateLineWidth`. Renderers must not capture the level.

## GUI, menus and screens (verified in the patched Minecraft and NeoForge sources, compiled, and the server side by GameTests; the screens are not yet seen in a running client)

- `GuiGraphics` is gone: screens draw into `net.minecraft.client.gui.GuiGraphicsExtractor`, and the render methods are `extract*`. `Screen.extractRenderState(graphics, mouseX, mouseY, a)` calls `extractBackground(...)` and then the widgets; `AbstractContainerScreen` adds `extractLabels(graphics, xm, ym)` (translated to the panel), `extractSlot`, `extractTooltip(graphics, mouseX, mouseY)` and `containerTick()`; its fields `leftPos`, `topPos`, `imageWidth`, `imageHeight`, `titleLabelX/Y`, `inventoryLabelX/Y`, `hoveredSlot` are protected. `AbstractContainerScreen.extractContents` draws `Screen`'s render state (background, then widgets) before slots and labels, so widgets sit below slot items.
- `AbstractContainerScreen.mouseClicked` returns true for every click it handles itself (patched 26.1.2.109 sources): after `super` (widgets via `ContainerEventHandler.getChildAt`, which skips widgets that are not `visible && active`) it runs the slot-click logic and ends with `return true`, even with no slot under the mouse. A container screen that hit-tests its own tabs or lists must do that before calling `super.mouseClicked`, never after `if (super.mouseClicked(...)) return true;`.
- Drawing a screen that is not open (guide previews, M7G 6b; patched 26.1.2.109 sources, compiled, not yet seen in a client): `Screen.init(int, int)` (and `resize`, `rebuildWidgets`) posts NeoForge's `ScreenEvent.Init.Pre/Post` to every mod as if the screen had opened, and `AbstractContainerScreen.extractRenderState`/`extractContents` post `ScreenEvent.Render.Foreground` and `ContainerScreenEvent.Render.Foreground`. To draw one quietly, a subclass sets the public `width`/`height`, calls its own protected `init()` (with `width == imageWidth`, `leftPos`/`topPos` are 0) and draws `extractBackground` (for `isInGameUi` screens a dark gradient over `width` x `height` plus `minecraft.gui.extractDeferredSubtitles()`, harmless), the public `renderables` list, then under `pose().translate(leftPos, topPos)` its protected `extractLabels` and `extractSlots`. `new Inventory(player, new EntityEquipment())` is an empty inventory for a client menu. `GuiGraphicsExtractor`'s scissor stack intersects a pushed rectangle with the one below (`ScissorStack.push`), so a nested `enableScissor` clips inside the outer one.
- `Player.isWithinBlockInteractionRange(BlockPos, double buffer)` checks the eye distance against `blockInteractionRange() + buffer`; `Level.isLoaded(BlockPos)` checks the chunk without loading it; `ByteBufCodecs.optional(codec)` carries an `Optional` (patched sources; `guide_live_*` GameTests).
- `GuiGraphicsExtractor`: `text(font, Component|String, x, y, argb, shadow)` (no `drawString`), `centeredText`, `fill(x0, y0, x1, y1, argb)`, `fillGradient(..., top, bottom)`, `outline(x, y, w, h, argb)`, `horizontalLine(x0, x1, y, argb)`, `item`/`fakeItem(stack, x, y)`, `setComponentTooltipForNextFrame(font, List<Component>, x, y)`, `pose()` (a `Matrix3x2fStack`), `enableScissor`/`disableScissor`.
- Sprites: `blitSprite(RenderPipelines.GUI_TEXTURED, Identifier, x, y, w, h[, int argbTint])` honours the sprite's `.mcmeta` GUI scaling (stretch, tile or `nine_slice`); `blitSprite(pipeline, id, spriteW, spriteH, u, v, x, y, w, h)` draws a region (how the furnace fills its arrow). Ids are relative to `textures/gui/sprites/` (`Identifier.withDefaultNamespace("container/slot")`). The tint multiplies the sprite.
- Useful vanilla GUI sprites (26.1.2 client jar): `recipe_book/overlay_recipe` 32x32, nine-slice border 4, is the classic light grey panel (0xC6 fill, white bevel, black rounded outline) and scales to any panel; `popup/background` is a dark panel; `container/slot` 18x18 (no mcmeta, so it stretches); `container/furnace/burn_progress` 24x16 is opaque grayscale (a white arrow on 0xC6), so an empty arrow has to be drawn separately; `recipe_book/tab` and `tab_selected` are 35x27 side tabs open on the right, placed 30 left of a panel 27 apart, the selected one drawn 2 further left so it covers the panel border; `widget/button[_highlighted|_disabled]` nine-slice 200x20 border 3, exposed as `AbstractButton.SPRITES`. Container backgrounds are whole textures under `textures/gui/container/`, not sprites.
- Fluid sprites in a GUI (Lib's `AccentTank`, patched 26.1.2.109 sources, compiled; not yet seen in a client): a fluid's sprites and tint come from its baked `FluidModel`, `Minecraft.getInstance().getModelManager().getFluidStateModelSet().get(fluid.defaultFluidState())`: `stillMaterial().sprite()` (a block atlas `TextureAtlasSprite`), and `fluidTintSource()` (nullable; `colorAsStack(FluidStack)` gives the GUI colour, often without alpha, so wrap it in `ARGB.opaque`). The name is `new FluidStack(fluid, 1, patch).getHoverName()`. `GuiGraphicsExtractor.blitSprite(RenderPipelines.GUI_TEXTURED, TextureAtlasSprite, x, y, w, h, argb)` binds `sprite.atlasLocation()`, so a block atlas sprite draws in a screen as is; the region overload for a `TextureAtlasSprite` is private, so draw whole 16 x 16 tiles inside `enableScissor` (which applies the pose) to show part of one.
- Mod GUI sprites: `assets/minecraft/atlases/gui.json` has a `directory` source `gui/sprites` with no namespace filter, so `assets/<modid>/textures/gui/sprites/<path>.png` is stitched into the GUI atlas and drawn with `blitSprite(..., Identifier.fromNamespaceAndPath(modid, path), ...)`; no `.mcmeta` means stretch. A white sprite tinted through the `int` overload takes any colour (Lib's `accent/icon_*` demo icons). `Font.lineHeight` is 9 (glyphs 8 tall); `GuiGraphicsExtractor.setTooltipForNextFrame(Font, Component, x, y)` shows one line (no `\n` split), `setComponentTooltipForNextFrame(Font, List<Component>, x, y)` several (patched sources, compiled; not yet seen in a client). For wrapped lines, `font.split(component, width)` each line and pass the result to `setTooltipForNextFrame(Font, List<? extends FormattedCharSequence>, x, y)` (patched sources 26.1.2.109, compiled).
- Client commands: `RegisterClientCommandsEvent` (NeoForge game bus, client; `getDispatcher()` is a `CommandDispatcher<CommandSourceStack>`, `getBuildContext()`) is posted by `ClientCommandHandler` on login; register `Commands.literal(...)` trees there. NeoForge patches `ChatScreen.keyPressed` to close the chat only if `minecraft.screen` is still the chat after the command ran, so a command can call `Minecraft.getInstance().setScreen(...)` directly (Lib's `/maxtech_lib accent_demo`; sources, compiled; not yet seen in a client).
- Widgets: `AbstractButton(x, y, w, h, message)` needs `onPress(InputWithModifiers)`, `extractContents(graphics, mouseX, mouseY, a)` and `updateWidgetNarration(output)` (`defaultButtonNarrationText`); `Button` has a protected constructor `(x, y, w, h, message, OnPress, CreateNarration)` with `DEFAULT_NARRATION`, and `Button.builder(message, onPress).bounds(x, y, w, h).tooltip(Tooltip.create(component)).build()`. `extractDefaultLabel(graphics.textRendererForWidget(this, GuiGraphicsExtractor.HoveredTextEffects.NONE))` draws a button label. `AbstractWidget.setTooltip`, `setMessage`, `active`, `visible`.
- Screens add widgets with the protected `addRenderableWidget`; `rebuildWidgets()` clears them and calls `init()` again. Inside a generic screen, an inner (non-static) class used from outside through the raw type loses its generic method signatures, so hand such helpers out as static nested classes. `setInitialFocus(GuiEventListener)` in `init()` focuses a widget when the screen opens (compiled).
- Data slots: vanilla's `ClientboundContainerSetDataPacket` writes id and value as shorts, but NeoForge's patched `ServerPlayer` synchronizer sends `AdvancedContainerSetDataPayload` (value as `VAR_INT`, data id as `short`, container id as `byte`) with the full int whenever the client has that channel, which every NeoForge client does. `broadcastChanges()` (the server calls it every tick for the open menu) compares each `DataSlot` with the value last sent and calls `ContainerSynchronizer.sendDataChange` only for changed ones; `setSynchronizer` first sends everything through `sendInitialData(menu, items, carried, int[] data)`. A test can install its own synchronizer (`createSlot()` returning `RemoteSlot.PLACEHOLDER` skips item sync) and replay the values into a client-side menu with `setData(id, value)`.
- `net.neoforged.neoforge.transfer.item.ResourceHandlerSlot(handler, IndexModifier, index, x, y)` is NeoForge's slot over a resource handler (`StacksResourceHandler::set` is an `IndexModifier`). It extends `StackCopySlot`: `getItem()` returns a copy and `setChanged()` writes the cached copy back, so vanilla's `moveItemStackTo` works on it. `mayPlace` asks `isValid`; `mayPickup` simulates an extraction in a root transaction. Vanilla `moveItemStackTo` merges into non-empty slots without asking `mayPlace` and checks it only for empty slots.
- Ordering of menu payloads against the menu (patched 26.1.2.109 sources, NeoForge `ClientPayloadHandler`, `ClientPayloadContext`, `PayloadRegistrar`; reasoned, not seen in a client): `ServerPlayer.openMenu` sends `ClientboundOpenScreenPacket` or NeoForge's `AdvancedOpenScreenPayload` before `initMenu`, so any payload sent from the menu's `broadcastChanges()` follows it on the connection. On the client the vanilla packet runs through `ensureRunningOnSameThread(..., minecraft.packetProcessor())` and every payload registered with the default `HandlerThread.MAIN` (NeoForge's open-screen one and ours) through `MainThreadPayloadHandler` -> `ClientPayloadContext.enqueueWork` -> the same `PacketProcessor.scheduleIfPossible`, so they run in arrival order and the menu exists before the first values payload is handled. The client sets `player.containerMenu` only when a screen factory is registered for the menu type (`MenuScreens.getScreenFactory(...).ifPresent`); without one, the payload meets the old menu and its container id check drops it. Lib's `ToolkitMenu` relies on this (`MenuValuesGameTests`).
- Menu buttons without a custom payload: the client calls `Minecraft.getInstance().gameMode.handleInventoryButtonClick(containerId, buttonId)` (`MultiPlayerGameMode`, sends `ServerboundContainerButtonClickPacket`, both ints); the server's `handleContainerButtonClick` drops it unless `containerId` matches the player's open menu, the player is not a spectator and `stillValid` holds, then calls `AbstractContainerMenu.clickMenuButton(player, buttonId)` (default `false`) and `broadcastChanges()` when it returns true.
- Components over the network: `ComponentSerialization.STREAM_CODEC` / `OPTIONAL_STREAM_CODEC` (both `StreamCodec<RegistryFriendlyByteBuf, ...>`) and the `TRUSTED_STREAM_CODEC` / `TRUSTED_OPTIONAL_STREAM_CODEC` variants vanilla uses for server-to-client text. A menu value that data slots cannot carry (a controller's form error) can go as a payload from an override of `broadcastChanges()`, which the server calls every tick for the open menu; send only when it changed (sources; the client side not yet seen in a running client).
- GUI item icons as an isometric picture (patched sources, compiled; not yet seen in a client): `GuiGraphicsExtractor.item(stack, x, y)` records a `GuiItemRenderState` with a copy of the current `pose()` (a JOML `Matrix3x2fStack`, so float `translate` and `scale` work). `GuiRenderState.findAppropriateNode` puts an element whose bounds overlap an earlier one's in a node above it, so overlapping items draw in submission order and painter's order (back to front) holds. Items are rendered into `GuiItemAtlas` slots of 16 × GUI scale pixels and then blitted, so scaling above 1 magnifies that image. A block item's GUI model (`gui` transform: 30° pitch, 225° yaw, scale 0.625) is a cube 10 px along an edge: about 7.07 px from the centre to a side corner, 3.54 px for the top face's half height, 8.66 px tall on screen; stepping icons by those amounts tiles them into a block stack.
- Real 3D in a GUI goes through picture-in-picture: `GuiGraphicsExtractor.submitPictureInPictureRenderState(PictureInPictureRenderState)` with a `PictureInPictureRenderer` (vanilla's are in `net.minecraft.client.gui.render.pip`: entity, skin, book, sign, banner, profiler chart), registered through NeoForge's `RegisterPictureInPictureRenderersEvent` (mod bus, client; `event.register(StateClass.class, bufferSource -> new Renderer(bufferSource))`), which fires at client startup, so a JEI plugin cannot register one; register it from a client `@EventBusSubscriber` (patched and NeoForge sources, compiled; not yet seen in a client).
- Client resource reload listeners: `AddClientReloadListenersEvent` (mod bus, client only; `net.neoforged.neoforge.client.event`) `addListener(Identifier key, PreparableReloadListener)`; a lambda cast to vanilla's `ResourceManagerReloadListener` (`onResourceManagerReload(ResourceManager)`) runs on each F3+T / resource pack change (NeoForge and patched sources). Used to drop `StructurePictureRenderer`'s cached quads.
- Reload listeners apply in their sorted order, one after another: `SimpleReloadInstance.prepareTasks` hands each listener a barrier that completes only after all preparations and the previous listener's whole reload, so `event.addDependency(VanillaClientListeners.MODELS, ours)` runs ours after the new baked models, atlases and fluid model set are in place; `Minecraft.reloadResourcePacks` calls `levelRenderer.allChanged()` only after every listener finished (patched sources 26.1.2.109). Lib repaints conduit contents there (`ConduitClient`).
- Lib guide pieces (M7G chunk 1; patched 26.1.2.109 sources, compiled, JUnit; not yet seen in a client): `SimplePreparableReloadListener<T>` has `prepare(ResourceManager, ProfilerFiller)` on the reload worker and `apply(T, ResourceManager, ProfilerFiller)` on the client thread (it extends NeoForge's `ContextAwareReloadListener`). `ResourceManager.listResources(String folder, Predicate<Identifier>)` returns `Map<Identifier, Resource>` over every namespace; `Resource.openAsReader()`/`open()`. ## Conduit rendering: per-quad chunk layers, translucent panes, atlas sprites (verified in the patched 26.1.2.109 and NeoForge `26.1.x` sources, by `runData` and by `ConduitGeometryTest`/`ConduitLookTest`; not yet seen in a running client)

- **A quad's chunk layer is the `layer` in its `BakedQuad.MaterialInfo`**: `SectionCompiler.compile` writes each quad to `quad.materialInfo().layer()`, and `MaterialInfo.of(Material.Baked, Transparency, tintIndex, shade, lightEmission, ambientOcclusion)` sets it to `ChunkSectionLayer.byTransparency(transparency)` (`hasTranslucent` -> TRANSLUCENT, `hasTransparent` -> CUTOUT, else SOLID). Only the `FaceBakery.bakeQuad(ModelBaker, ...)` overload works the transparency out from the sprite's pixels (`computeMaterialTransparency`, or TRANSLUCENT when the material is `forceTranslucent`); the `bakeQuad(ModelBaker.Interner, ...)` overload a dynamic model calls uses the `MaterialInfo` it is given. So a model puts glass in the translucent layer by passing `Transparency.TRANSLUCENT`, and gets a sprite's own answer from `sprite.contents().transparency()`. There is no render type per part or per model in 26.1; this refines the "Chunk layer per quad" entry above, which holds for JSON models.
- `BlockStateModel.materialFlags()` (`BakedQuad.FLAG_TRANSLUCENT` = 1, animated = 2) does not pick chunk layers. `LevelRenderer.extractBlockOutline` reads it for `ExtractBlockOutlineRenderStateEvent`'s translucent flag, `BlockFeatureRenderer` for moving (piston) blocks and `BlockStateModelWrapper` for a block model shown as an item; NeoForge's `materialFlags(level, pos, state)` defaults to it. - `RenderPipelines.TRANSLUCENT_TERRAIN` culls back faces: `RenderPipeline.Builder` defaults `cull` to true and only some pipelines call `withCull(false)`. A pane meant to be seen from both sides needs a quad facing each way.
- `assets/minecraft/atlases/blocks.json` has a `directory` source `block`, so every namespace's `textures/block/**` is stitched into the block atlas; `ModelBaker.materials().get(new Material(id), debugName)` finds such a sprite at bake time without `resolveDependencies` naming it.
- `CuboidFace.UVs(minU, minV, maxU, maxV)` is a public record in pixels; `new CuboidFace.UVs(0, 0, 16, 16)` draws the whole sprite on a face of any size. `SpriteContents.transparency()` is the whole sprite's `Transparency`.
- Face UVs and turns in `FaceBakery.bakeQuad`: vertex `i` walks the face in `FaceInfo` order (UP: min x/min z, min x/max z, max x/max z, max x/min z; the other faces likewise start top left as `defaultFaceUV` lays them out) and takes corner `(i + quadrant.shift) % 4` of the `UVs` (min/min, min/max, max/max, max/min; `CuboidFace.getU/getV`). So `defaultFaceUV(from, to, facing)` shows each vertex the sprite pixel at its position in the block, and a rectangle turned by `(u, v) -> (v, 16 - u)` per quarter, paired with `Quadrant` of that many quarters, keeps that block projection turned clockwise: the sprite's +v then runs along the face's -u, -v and +u for R90, R180, R270. `Quadrant.values()` is in shift order. Lib's `ConduitUvs` builds on this; `ConduitFaceUvsTest` checks it against `FaceInfo` and `CuboidFace.getU/getV` in JUnit, without a client or sprite. Not yet seen in a client.
- A mod can fire its own client mod-bus event from its `RegisterBlockStateModels` listener with `ModLoader.postEvent(...)`: that event fires once in `ClientHooks.initClientRegistries()`, after registration and before the first model bake, and the nested post reaches every mod's listeners (Lib's `RegisterConduitModelsEvent`; seen starting a client 2026-11-27, the hooked model's drawing not yet seen in a running client). `ModelEvent.ModifyBakingResult.getTextureGetter()` takes the atlas id (`ns:block/name`).
- `ExtraCodecs.STRING_RGB_COLOR` reads `#RRGGBB` as an opaque ARGB int and writes lower-case hex (`#dcdcdc`); it also accepts an int or a float vector. `Identifier.withPrefix`/`withSuffix` change the path.

# GameTests

## GameTests (verified with `:storage:neoforge:runGameTestServer`)

- The game process of `runGameTestServer` inherits the environment of the `./gradlew` call: an env var set for `./gradlew :lib:neoforge:runGameTestServer` reached `System.getenv` in the server (verified on Windows with the daemon; CI uses `--no-daemon`). `PerfBudget` reads `MAXTECH_PERF_BUDGETS_WARN` that way.
- A creative tab's contents can be checked on the GameTest server: `tab.buildContents(new CreativeModeTab.ItemDisplayParameters(level.enabledFeatures(), false, level.registryAccess()))` runs the `displayItems` generator (through NeoForge's `BuildCreativeModeTabContentsEvent` hook), then `getDisplayItems()` returns the stacks in order (`content_creative_tab`).
- Tests are data: a test **function** (`Consumer<GameTestHelper>`) registered in `Registries.TEST_FUNCTION`, plus a test **instance** (`FunctionGameTestInstance(ResourceKey<Consumer<GameTestHelper>>, TestData<Holder<TestEnvironmentDefinition<?>>>)`) registered in `RegisterGameTestsEvent` (mod bus) via `registerEnvironment(Identifier, TestEnvironmentDefinition<?>...)` and `registerTest(Identifier, GameTestInstance)`. JSON under `data/<ns>/test_instance/` works too (Documentation `misc/gametest.md`).
- `TestData(environment, Identifier structure, int maxTicks, int setupTicks, boolean required)`. The structure must exist as `data/<ns>/structure/<path>.nbt`; Lib and Storage ship their own empty templates (`maxtech_lib:empty_1x1x1`, `maxtech_storage:empty_42x4x27`, ...) under `src/gametest/resources`. NeoForge's own empty templates come from a reflection hack in its testframework; don't copy that.
- Structure NBT DataVersion for 26.1.2 is **4790** (`version.json` `world_version`).
- `@EventBusSubscriber(modid = ...)` with no bus argument routes `IModBusEvent`s to the mod bus; that is how GameTest classes subscribe without touching the entrypoint.
- The game test server also runs vanilla's built-in test in `minecraft:default` ("All 2 required tests passed" with one of ours). It exits with the number of failed required tests, so a failing test fails the Gradle task (verified with a deliberate `helper.fail`). It needs no EULA file.
- Our convention plugin gives every `neoforge` project a `gametest` source set, loaded only as part of that project's own mod and compiled by `check`. Because it is part of the mod in every dev run, anything it registers (e.g. test conduit types) also exists in `runClient` and `runData`, never in the jar.
- Batches are grouped by environment holder and run **one after another** (`GameTestBatchFactory` groups by `batch()`, `GameTestRunner.runBatch(i + 1)` starts when the previous batch is done; at most 50 tests per batch). Tests that change global state such as a config value each get their own `event.registerEnvironment(id)` so they never overlap (verified with `NetworkGameTests`: the log shows one "Running test environment ..." line per environment). The batch order changes from run to run: `GameTestBatchFactory` groups with `Collectors.groupingBy` into a `HashMap` keyed by the environment `Holder`, whose (NeoForge-patched) `hashCode` is its `ResourceKey`'s, an identity hash since `ResourceKey` does not override it (two `runGameTestServer` runs of the same tests ran the machine perf batches at different points). A test must not rely on another batch having run before it, or on what earlier batches left in the level.
- `GameTestHelper.assertValueEqual(value, expected, name)`: actual value first, and it calls `value.equals`, so don't pass `null`. Its message fills `"Expected %s to be %s: was %s"` with `(name, value, expected)`, so a failure reads backwards ("to be <actual>: was <expected>"); the argument order is still right (verified by a deliberately failing perf test). `helper.assertionException(Component)` returns the exception to `throw` where a method must not return; `fail(String)` throws.
- `GameTestSequence.thenExecute` catches a failed assertion with `parent.fail(e)` and goes on with the next steps in the same tick, so after a failure later steps run on wrong state and the test reports the **last** failure, not the first (patched sources; seen while breaking the `logic_editor_*` tests on purpose). When a failure message makes no sense, look at the steps before it.
- `GameTestSequence.thenWaitUntil(Runnable)` reruns its runnable every tick while it throws a `GameTestAssertException` (swallowed by `tickAndContinue` until `maxTicks`; then `tickAndFailIfNotComplete` reports that exception), so a stateful runnable can run a variable number of ticks in one step, as `PerfBudget.measureTicks` does for its retry. An assertion of the test inside such a step would only keep it waiting, so catch it and pass it to `helper.testInfo.fail(e)`. A sequence's events cannot be added to while it ticks (they are walked with an iterator), but `helper.startSequence()` from a step adds a new sequence that ticks from the next tick (`GameTestInfo.sequences` is copy-on-write; patched sources).
- Driving interactions in a test: `stack.useOn(new UseOnContext(player, hand, blockHitResult))` after `player.setItemInHand(hand, stack)`; `state.useWithoutItem(level, player, hit)` and `state.useItemOn(stack, level, player, hand, hit)` call the block directly; `player.setShiftKeyDown(true)` makes a mock player sneak.
- Every mod's `neoforge` project has its own GameTests; structure templates are per namespace, so a mod's tests need their own copies under `data/<modid>/structure/`.
- `helper.makeMockPlayer(GameType.CREATIVE)` only overrides `gameMode()`; its abilities stay survival, so `preventsBlockDrops()` (`abilities.instabuild`) is false until the test sets `player.getAbilities().instabuild = true` (found by `machine_creative_break_keeps_contents`). Creative-only drops like the shulker box's go in `Block.playerWillDestroy(Level, BlockPos, BlockState, Player)`, guarded by `player.preventsBlockDrops()`.
- `SignalGetter.getSignal(pos, direction)` reads the block at `pos` and, for a redstone conductor, `getDirectSignalTo(pos)` reads its neighbours too; a redstone wire there reads further (`RedStoneWireBlock`), so a `hasNeighborSignal` read can touch blocks up to three away and load chunks. Loading a chunk sends no neighbour updates to blocks in the next chunk, so a block that caches its signal must save it and re-read once the chunks around it are present.
- `helper.makeMockPlayer(GameType)` gives a player that is not added to the level; position it with `snapTo` and `lookAt` to drive per-part block interactions.
- `helper.getLevel().getServer().getServerDirectory()` is the run's game directory (`runs/<project>/gameTestServer` with our convention plugin), a place a GameTest can write files for a developer to read (`content_dump`).
- A machine placed with `helper.setBlock` joins its scheduler only in `onLoad`, on the next block entity pass, so "not awake and idle" holds at tick 0 before it ever ticked; wait for `ticks() > 0` too. Placing a conduit next to a machine sends it a neighbour update, which wakes it, so a test of another wake-up event must not place blocks around it at the same time (found by `combustion_generator_sleeps_when_full`).
- Tests are laid out with 5 blocks between columns and 6 between rows (`StructureGridSpawner`), so blocks placed outside the test's structure can hit a neighbour; use a structure of the right size. `maxtech_lib:empty_7x2x3` and `maxtech_lib:empty_42x4x27` exist; empty air structures are plain gzipped NBT (`DataVersion`, `size`, one-entry `palette` of `minecraft:air`, a `blocks` entry per position ordered y, then z, then x fastest, empty `entities`). The shipped files write that empty `entities` list with element type 0 (TAG_End); a copy written that way is byte-identical to the shipped ones.
- Per-batch setup and teardown: implement `TestEnvironmentDefinition<T>` (`T setup(ServerLevel)`, `teardown(ServerLevel, T)`, `codec()`), register its `MapCodec` in `Registries.TEST_ENVIRONMENT_DEFINITION_TYPE` (a `DeferredRegister`/`Platform.registry()` registrar works), and pass an instance to `registerEnvironment(id, definition)`. `GameTestRunner` activates it after placing the batch's structures and before the tests tick, and `endCurrentEnvironment()` tears it down when the next batch starts, when all batches are done, on `stop()` and on a halting failure, so a failed test still gets its teardown.
- After each batch the runner un-forces every force-loaded chunk (`setChunkForced(x, z, false)`), so earlier test areas may unload while later batches run.
- The game test server never clears finished tests: it builds its runner with `StructureGridSpawner(startPos, 8, false)` and without `clearBetweenBatches()`, and every batch continues the same grid. Whatever a test built stays in the level and keeps working (e.g. a powered network keeps delivering) while later batches run, under their config. `perf/` scenarios therefore remove their blocks in an environment teardown (`PerfEnvironment`). A batch's teardown runs after the next batch's structures are placed (`runBatch` calls `createStructuresForBatch` before `endCurrentEnvironment`), in the same tick the old chunks are un-forced, so they are still loaded then (verified by a teardown clearing a perf area).
- `registerEnvironment(id, a, b)` wraps the definitions in `TestEnvironmentDefinition.AllOf`, which sets them up in order and tears them down in reverse. A stateless definition can use `MapCodec.unit(instance)` and `net.minecraft.util.Unit` as its saved data.
- Test runnables run after every level has ticked in the same server tick (`MinecraftServer.tickChildren` ticks levels, including the level tick events, before `GameTestTicker`), so a `helper.onEachTick` runnable sees the results of the tick that just ended. The game test server runs ticks back to back rather than at 20 TPS (500 ticks took under a second), so tick counts, not wall time, bound a test.
- `System.nanoTime()` on the owner's Mac (Apple silicon, JDK 25) ticks in steps of about 41.7 ns: an empty profiled scheduler tick reads as 41 or 42 ns. Budgets below about 0.1 µs cannot be measured.
- `GameTestHelper.onEachTick(action)` puts `action` in the test's run-at-tick map once for every tick from the current one to the timeout; `GameTestInfo.tickInternal` runs that map before the sequences. So a runnable added from a sequence event first runs on the next test tick, after the level (and every machine in it) has ticked once more. Do the first round directly as well when the level must see it at once.
- `BuiltInRegistries.ITEM.getTagOrEmpty(TagKey<Item>)` returns an `Iterable<Holder<Item>>` of the loaded tag in a GameTest, e.g. to pick one item of each tag a crafting shape names and match it with `recipeAccess().getRecipeFor(RecipeType.CRAFTING, CraftingInput.of(3, 3, grid), level)` (`component_crafting`).
- `-Pgametest.repeat=N` (`--repeatCount`) puts the N copies of a test into the same batch, running at the same time,
  so tests that read or reset server-wide state (a shared per-tick budget, a global job count, a cleared registry)
  fail against their own copies; repeat whole runs instead (seen with `setup_build_*`, 2026-10-15).
- The game test server ticks as fast as it can (about 2,200 ticks in under a second for `perf_display_unseen_screens`), so a long perf warmup costs almost nothing. A perf window shortly after the code first runs measures the interpreter and C1, not compiled code: the busy display scenario measured about 0.05 ms per tick after 100 warmup ticks, 0.011 after 2,000 and 0.006 over 20,000 (seen 2026-10-15). A perf test whose path is new to the JVM in its batch needs a warmup of about 2,000 ticks. `-Pgametest.repeat=N` runs the N copies at once in the same level, so it multiplies a perf test's load instead of repeating it; repeat with separate Gradle calls.
- `--tests` (our `-Pgametest`) takes one namespaced id pattern with wildcards, not a list (`GameTestMainUtil`); a comma-separated list fails silently, running only the tests of its first pattern (seen 2026-10-07), so run one Gradle call per pattern. To reproduce an interaction between two batches, pick one pattern that matches both and few others and rerun it: batch order is random each run, so the pair lands next to each other far more often than in the full suite. That is how issue #93 (three maintenance-test controllers still running recipes into `perf_machines_idle`) was reproduced; any test that ends with a machine still working must clear its area in teardown.
- In zsh, quote the `-Pgametest` pattern, or the shell expands the `*` itself and fails with "no matches found".
- `-Pgametest` knows only `*` wildcards: a character class such as `maxtech_storage:logic_[rp]*` matched no test and
  failed the run ("Test selection matcher ... found no tests", seen 2026-10-08).
- A runnable that throws does not stop the next tick's runnable: `GameTestInfo.tick` calls `finish()` on an error and then still runs `tickInternal()` once more, and an exception there replaces the first error. Make `onEachTick` runnables return early once they have asserted (verified: an out-of-bounds sample index hid the real assertion).
- `ConfigValue.set(...)` only changes the loaded config in memory; any reload from disk (the file watcher calls `ConfigTracker.loadConfig`, which replaces the loaded config) discards it. Tests that switch a value must also `save()` it. FML adds the file's watch only after creating and loading it (`ConfigTracker.openConfig`), but night-config's `FileWatcher` watches the whole directory, and on macOS the JDK uses `sun.nio.fs.PollingWatchService` (2 s poll, snapshot at registration). `config/` is already watched for NeoForge's common config, so after a fresh run directory creates `maxtech-server.toml` the next poll reports it as created once the handler exists, and FML reloads it 0.5–2.5 s after server start (found in review of PR #23 from the FML and night-config sources; not seen in a log because FML's CONFIG debug lines are off). On Linux, inotify likely delivers the event before the handler exists, so it is ignored.
- Saving does not make a switched value safe from a watcher reload either. Any save changes the file, so the next poll reloads it; night-config runs the handler (FML's `ConfigWatcher`) on its own executor thread 500 ms after the poll (`DebouncedRunnable`). The handler holds the `ModConfig`'s lock, one `ReentrantLock` per mod shared by all its configs, from reading the file until `setConfig` has replaced the loaded config and fired `ModConfigEvent.Reloading`. `ConfigValue.set` takes no lock, and `ModConfigSpec.save()` (`LoadedConfig.save`) writes the file **outside** the lock and only then fires `Reloading` under it. So a server-thread `set` + `save` that lands between the watcher's read and its replace is undone in memory until the next poll: that put `burn` back into `energy_overload_none` (issue #43; reproduced by setting `burn` in memory at the start of the test, which gives the CI failure's exact message). `FileWatcher.removeWatch` is no alternative: it only removes the handler from the map, and a debounced run already scheduled still fires (night-config 3.8.3 sources).
- Only the `Reloading` event of your own save is safe to change the config from. `LoadedConfig.save` (FML 11.0.15) calls `ConfigTracker.writeConfig` (night-config `WritingMode.REPLACE_ATOMIC`) first, then takes the lock and fires `Reloading` through `ModContainer.acceptEvent`, a synchronous `bus.post`; so that event runs on the saving thread, under the lock, after its write. Taking a pending change from the watcher's event instead (as PR #61 first did) leaves a gap: the watcher sets and writes the new value, but the saving thread's own write, outside the lock, can still land afterwards with the old config, and the next poll loads the old value back.
- A test can switch a server config value with `ModConfigSpec.ConfigValue.set(...)`: our `ConfigBuilder` returns NeoForge's `ConfigValue` objects, so `ServerConfig.X instanceof ModConfigSpec.ConfigValue<T> v` works in `neoforge` code.
- `GameTestSequence.thenExecute` catches the runnable's `GameTestAssertException`, fails the test with it and goes on with the next events in the same tick; `thenWaitUntil` retries its runnable every tick until it passes. `GameTestInfo.fail` overwrites the stored error, so after a failed `thenExecute` a later failing event's message is the one reported.
- Lib's `ConfigFile.set(path, value)` (NeoForge `ConfigValue.set`, no `save`) changes a server config value in memory only: nothing is written, so no watcher reload can undo it, and the `ServerConfig` suppliers return it at once. A GameTest batch environment sets it in `setup` and puts it back in `teardown`, which runs also for a failed test (`EnergyConfigEnvironment`, verified by the `energy_edge_*` batches).
- `GameTestSequence.thenExecuteFor(int ticks, Runnable)` exists in 26.1.2 and runs the runnable on each of the next `ticks` ticks, so a per-tick invariant (such as no energy made in a loop) needs no hand-rolled counter (`fe_converter_loop_makes_nothing`).
- `GameTestHelper.findEntities(EntityType, x, y, z, distance)` takes test-relative coordinates and only searches the test's structure bounds; `assertItemEntityNotPresent(Item)` checks the whole structure; `getTick()` counts the test's ticks, one per server tick, so it can time travel exactly.

- The runner can spend many ticks between setting up a batch's environment and the batch's first test tick (a clock set to 30 ticks before sunrise in `setup` was well past sunrise by then), so state that must hold at a test's start, such as the time of day, belongs in the test function (found by `solar_wakes_at_sunrise`).
- Test structures are enclosed in barrier blocks: there is a barrier right above the structure's top layer. Barriers pass light, so `canSeeSky` stays true inside, but they are motion-blocking, so `precipitationAt` is `NONE` for every position in a test (found by `solar_rain_scales_output`). The game test world is the flat preset with plains.
- Weather in a test: `level.getWeatherData().setRaining(true)` and `level.setRainLevel(1.0F)` make `isRaining()` true at once; NeoForge's game test rules turn `advance_weather` off, so it stays until a teardown resets both. `advance_time` stays on, so the clock runs (patched `GameTestServer`; `solar_rain_scales_output`).
- A config of another mod fires its `ModConfigEvent.Reloading` on that mod's bus, which a `@EventBusSubscriber(modid = ...)` class of the test's mod never sees; add the listener to that bus with `ModList.get().getModContainerById(id).map(ModContainer::getEventBus)` and `addListener(ModConfigEvent.Reloading.class, ...)`.
- `NeoForge.EVENT_BUS.post(event)` returns the event, so a test can post `new PlayerInteractEvent.RightClickBlock(player, hand, pos, hit)` and read `isCanceled()` and `getCancellationResult()` (`transformer_screwdriver_rebuilds_routes`).
- A `ServerPlayer` for handler tests can be built without joining: `new ServerPlayer(level.getServer(), level, new GameProfile(UUID.randomUUID(), name), ClientInformation.createDefault())` (it registers stats and advancements with the player list but opens no connection). Its `connection` is null, so position it with `setPos`, not `snapTo`: `ServerPlayer.snapTo` calls `connection.resetPosition()` and throws. Set `player.containerMenu` to a server menu built directly, and have that menu send its payloads to a collector instead of `Platform.network()`.
- Commands: `RegisterCommandsEvent` (game bus) `getDispatcher().register(Commands.literal(name).requires(Commands.hasPermission(Commands.LEVEL_GAMEMASTERS)).executes(context -> ...))`; permission levels are `PermissionCheck` objects in 26.1 (`TimeCommand`), and `context.getSource().getPlayerOrException()` gives the `ServerPlayer`. A gametest-source-set class registering one gives a dev-only command.

## Game test server output and CI annotations (verified in the patched 26.1.2.109 sources, a CI run log and local `runGameTestServer` runs)

- **`System.out` is not the real stdout once the game has bootstrapped.** `Bootstrap.bootStrap()` calls `wrapStreams()`, which replaces `System.out`/`System.err` with `LoggedPrintStream`s that log every line as `[STDOUT/]` with a timestamp prefix. `Bootstrap.realStdoutPrintln(String)` (public static) prints to the original stdout instead.
- **`runGameTestServer` forwards the server's stdout to Gradle's, and a CI step's log shows it line by line** (the Build workflow's GameTests step carries every `[Server thread/INFO]` line). A line printed with `Bootstrap.realStdoutPrintln` starts at column 0 there, so a GitHub Actions workflow command such as `::warning title=...::...` can come straight from a GameTest, with no grep step in the workflow (the line is verified at column 0 in a local Gradle run; the annotation itself is not yet seen on CI, whose runners are not busy enough to skip a budget).

# Lib runtime

## Standalone conduit blocks (verified in the NeoForge `26.1.x` and patched 26.1.2.109 sources and by the `conduit_*`, `wrench_*` and `facade_*` GameTests)

- Registration order: `GameData.postRegisterEvents` posts one `RegisterEvent` per registry, to every mod in mod order, before moving to the next registry; the order is attributes, data components and particle types, then vanilla's registries in vanilla order (blocks, items, ..., block entity types), then modded registries such as `maxtech_lib:conduit_type` sorted by id. `BlockEntityTypeAddBlocksEvent` (mod bus, after all registration) is the event for adding blocks to someone else's type.
- `LevelChunk.setBlockState` calls the new state's `onPlace` before it creates the block entity, so `Block#onPlace` sees no block entity of its own. The neighbours' `neighborChanged` runs afterwards from `Level.setBlock`, by which time the new block entity exists; a placed block that must look at its neighbours does it in `onLoad` (the next block entity pass), or the code that placed it calls it directly (`ConduitBlock.placeConduit` does, so tests can check links in the same tick).
- Which neighbour callback sees a block entity coming or going beside a block (patched 26.1.2.109 `Level` sources; `conduit_api_attach_*` GameTests): `Level.setBlock` with `UPDATE_NEIGHBORS` (1; `GameTestHelper.setBlock` uses 3) calls `updateNeighborsAt`, so every neighbour's `neighborChanged` runs after a block is placed, broken or replaced, once the new block entity exists. NeoForge's `IBlockExtension.onNeighborChange` runs only from `updateNeighbourForOutputSignal`: a neighbour's `BlockEntity.setChanged()` (every container change, so too hot for attachment checks), a placed block with an analog output signal, and NeoForge's patched `Level.removeBlockEntity`; `Level.setBlockEntity` notifies nobody. A chunk reaching full status sends neither, so Lib's attaching conduits (`ConduitAttachments`) listen to `ChunkEvent.Load` plus `ChunkTicketLevelUpdatedEvent` into full and re-read at the level tick's end once `getChunkNow` sees the chunk.
- Chunk load and `onLoad` order (patched 26.1.2.109 `ChunkStatusTasks.full`, `GenerationChunkHolder.applyStep`, `Level.tickBlockEntities`): `ChunkEvent.Load` fires inside the main-thread task that builds the `LevelChunk`, and the holder's FULL future completes in that same task (`applyStep(...).handle` runs inline), so `getChunkNow` sees a chunk from the end of its Load task on. `BlockEntity.onLoad` never runs in that task: `addAndRegisterBlockEntity` queues the block entity in `freshBlockEntities`, and `onLoad` runs at the start of the next `tickBlockEntities` (inside `ServerLevel.tick`, after `getChunkSource().tick` processed the chunk tasks). So when two neighbouring chunks load in one tick, both Load events come before either chunk's `onLoad`, and every `onLoad` sees the other chunk readable; a listener keyed on block entities registered in `onLoad` misses its neighbour's Load, but `onLoad` itself reads the neighbour (sources only: a GameTest cannot make two chunk loads land in one tick). Leaving full status: `ChunkTicketLevelUpdatedEvent` (old ≤ 33, new > 33) fires before `updateHighestAllowedStatus`, which disallows FULL within the same `runAllUpdates`, and `runDistanceManagerUpdates` then clears `ServerChunkCache`'s last-chunk cache, so `getChunkNow` is null by the level tick's end with no wait (`conduit_attach_chunk_unload`). `LevelEvent.Unload` fires for each server level from `MinecraftServer.stopServer`, before `ServerStoppedEvent`.
- Reading a block across a chunk border loads that chunk: `Level.getBlockState`/`getBlockEntity` go through `getChunk(x, z, FULL, true)`, so a `setBlock` with neighbour or shape updates next to a chunk that is not at full status loads it synchronously. A GameTest that needs a neighbour chunk to stay away sets its blocks with `UPDATE_CLIENTS | UPDATE_KNOWN_SHAPE` (2 | 16). One forced chunk far from the test grid keeps a chunk two away at full status (level 33) and one three away below it, which `conduit_api_attach_chunk_load` uses to load a neighbour's chunk after the conduit is in place (sources; the test passes and fails without the chunk listener).
- A block registered without a generated loot table (a GameTest-only conduit block) drops nothing when broken; `getDrops` can add to the loot table's list (a conduit adds its facade).
- `Error Prone`: `IdentityHashMapUsage` also fires for a `volatile Map<K, V>` field assigned `new IdentityHashMap<>()`; fastutil's `Reference2ObjectOpenHashMap` is the identity map that passes. `ReferenceEquality` fires for `==` between `ConduitType`s, `Block`s and `BlockEntityType`s as well; use `equals` (identity for these classes).

## FE buffers and server ticks for Lib's runtime (Lib A; verified in the NeoForge 26.1.2.109 sources, by compiling and by the `fe_buffer_capability` and `worker_pool_commits_on_server_thread` GameTests)

- `SimpleEnergyHandler` is a `SnapshotJournal<Integer>` (boxes a snapshot per transaction) with `int` amounts only; Lib's
  `FeBuffer` keeps a `long` with pooled `long[]` snapshots instead.
- `EnergyHandlerUtil.move(from, to, amount, null)` opens its own transaction (`Transaction.open(null)`), simulates the
  extract in a nested one, inserts, then extracts exactly what was inserted and returns 0 (rolled back) when `from`
  gives less the second time.
- `ServerTickEvent.Post` (`net.neoforged.neoforge.event.tick`, game bus) has `getServer()`; it fires after every level
  ticked, which is where `WorkerPool` commits background results.
- Error Prone fails the build on `Thread.setPriority` (`ThreadPriorityCheck`) and on `==` between `Thread`s
  (`ReferenceEquality`).

## Stack keys and palette codecs (Lib A; verified in the NeoForge 26.1.2.109 and patched sources, by compiling and by the `resource_keys_round_trip` GameTest)

- `ItemResource.of(ItemLike, DataComponentPatch)` and `FluidResource.of(Fluid, DataComponentPatch)` exist, and both have
  `getComponentsPatch()`; vanilla's public `ItemStack(Holder<Item>, int, DataComponentPatch)` builds a stack from a patch.
  An `ItemResource` built from a key equals `ItemResource.of(stack)` for the same stack.
- `DataComponentPatch.hashCode()` is its map's hash, computed on every call, so a key used in hash maps caches it.
- `Codec.INT_STREAM` and `Codec.LONG_STREAM` encode through `NbtOps` as `IntArrayTag` and `LongArrayTag`.
- Error Prone fails the build on a record with array components (`ArrayRecordComponent`) and on `==` between `Item`s or
  `Fluid`s (`ReferenceEquality`; registry entries never override `equals`, so a class-level suppression with that reason
  is fine).

## Lib scheduler: tasks moved between groups (M6c2 area G; `TaskSchedulerTest`)

- A `ScheduledTask` carries one `queued` flag, not one per group. When a queued task moves to another `TaskGroup` (`add` on the new group, as a storage network merge does for every device task), the new group cannot queue it; the old group's next pass hands it over (`runOne`), and since this fix `close()` does the same for a closed group's queue. Before it, a task that was queued when its network merged away slept until its next `wake()`.

## Saved data versions and migration (Lib `lib.save`; verified 2026-10-15 in the patched 26.1.2.109 and DataFixerUpper 9.0.19 sources, by `SaveFormatTest` and the `save_compat_*` GameTests)

- `BlockEntity.loadWithComponents` and `loadCustomOnly` are `final` and both only call `loadAdditional(ValueInput)`, and
  a subclass's `loadAdditional` reads the same `ValueInput` object its super got, so a root class cannot hand migrated
  data down through `loadAdditional`. Lib's `VersionedBlockEntity` makes `loadAdditional` final and calls
  `loadSaved(migrated)`; subclasses override `loadSaved`.
- The whole of a `ValueInput` as a tag: `input.read(MapCodec.assumeMapUnsafe(CompoundTag.CODEC))`
  (`TagValueInput.read(MapCodec)` decodes the input's map with its registry ops; the result shares child tags, so copy
  before changing). A new input over a tag: `TagValueInput.create(ProblemReporter.DISCARDING, input.lookup(), tag)`.
  `TagValueInput.create(..., HolderLookup.Provider.create(Stream.empty()), tag)` works in plain JUnit.
- `CompoundTag.getIntOr(key, default)` reads any `NumericTag`; `copy()` is deep. `NbtOps.mergeToMap(map, key, value)`
  shallow-copies a compound (or makes one from `EndTag`) and errors for anything else; `NbtOps.remove` returns a copy
  without the key. `ops.convertTo(NbtOps.INSTANCE, value)` and back move data between any ops (JSON too).
- `SavedDataType(Identifier, Supplier<T>, Codec<T>)` is the three-argument constructor (NeoForge made the
  `DataFixTypes` nullable); the codec sees the saved data's own map, inside the file's `data` compound.

## Items used on mobs (Farms sampler; verified in the patched 26.1.2.109 sources and by the `sampler_*` GameTests)

- `Player.interactOn` fires `PlayerInteractEvent.EntityInteract` (both sides; the client calls `interactOn` from `MultiPlayerGameMode.interact`), then `entity.interact` (villagers trade, horses mount), and only if that passes `stack.interactLivingEntity`, on a copy of the stack for a player with infinite materials. An item that must win over the mob cancels the event with `setCancellationResult`.
- Hold-to-use: `startUsingItem(hand)` from `interactLivingEntity` runs `getUseDuration` ticks of `onUseTick`; `completeUsingItem` (server only) calls `finishUsingItem`, release calls `releaseUsing`, and every path ends in NeoForge's `Item.onStopUsing(stack, entity, count)`. `user.stopUsingItem()` inside `onUseTick` cancels. `CommonHooks.canContinueUsing` keeps the use going when the hand gets a new stack of the same item (an FE charger's `exchange`).
- `Entity.is(TagKey<EntityType<?>>)` checks entity type tags (`EntityType` itself has no `is(TagKey)`); NeoForge's `c:bosses` holds the ender dragon and the wither. `Player.sendOverlayMessage(Component)` is the action bar message (a no-op on a plain mock player). Error Prone's `EnumOrdinal` fails `Enum.ordinal()` calls, but not a `SomeEnum::ordinal` method reference.
- `DataComponentType.Builder.ignoreSwapAnimation()` keeps a component change (charge) from replaying the hand's equip animation.
